# 15 — Словарь сущностей и законы ядра (v3 · 2026-09-22)

Главный словарь. Если другой документ называет вещь иначе — действует этот файл, а старое место
перечислено в §10.

**Правило словаря:** одно слово — один смысл. Новое слово появляется только тогда, когда доказано,
что существующими задачу выразить нельзя.

**Что убрано в v3 и почему:**
- **FAMILY** — убрано. «Перекрасить все полки» — это не сущность, а область применения (SCOPE).
- **ROLE** — убрано. Роль и тип отвечали на один вопрос «что это». Остался **TYPE**.
- **CONTACT** — переименовано в **JOINT** и стало локальным: свой стык в каждой точке.

---

## 1. Три приложения

```
APP 1 — вся мебель                 APP 2 — одна ячейка            APP 3 — одна деталь
                                                                   
SET                                UNIT                            COMPONENT
 ├── MODULE                         └── SPACE                        └── PART
 │    ├── UNIT                           ├── COMPONENT                    точная форма:
 │    ├── UNIT   ← общие детали           │    └── PART                    вырезы, фаски,
 │    └── UNIT                            ├── PATTERN                      окно в двери
 │                                        │    └── COMPONENT × N
 └── MODULE                               └── вложенный SPACE
```

App 1 расставляет и объединяет. **App 2 строит один UNIT — это главный конструктор.**
App 3 занимается формой отдельной детали.

## 3. Сущности

### E01 — SET
Вся мебель целиком: кухня, гардеробная, стенка. Содержит модули и юниты. Верхний уровень App 1.

### E02 — MODULE
Несколько **соседних юнитов, которые строятся вместе и могут делить физические детали**:
боковину, дно, крышку, задник, цоколь.

```
Три отдельных юнита          Один модуль из трёх юнитов
┌──┬──┐┌──┬──┐┌──┬──┐        ┌──┬─────┬─────┬──┐
│  │  ││  │  ││  │  │        │  │     │     │  │
└──┴──┘└──┴──┘└──┴──┘        └──┴─────┴─────┴──┘
6 боковин                     4 боковины: две общие
```

Ядро **считает и показывает выгоду** («общая боковина: −1 деталь, −0.34 м²»), но **не объединяет
само** (Z09). Модуль существует ровно ради общих деталей — этим он отличается от группы (§8).
**Модуль живёт только в App 1.**

### E03 — UNIT
Одна ячейка мебели: нижняя тумба, верхний шкаф, пенал, антресоль, открытая секция.
**App 2 работает с одним юнитом.** Внутри юнита есть корневое пространство:

```
UNIT 600 × 720 × 560
└── SPACE 568 × 688 × 560
```

Слово «шкаф» не подходит: юнит бывает открытой полкой, нишей под телевизор, коробом.

### E04 — SPACE
Свободный объём, куда можно ставить. Пространства бывают вложенными: внутри юнита, внутри ящика,
между полками паттерна.

### E05 — COMPONENT
Одна конкретная вещь на сцене: `Ящик #12`, `Дверь #4`, `Полка #7`. Всегда знает свой тип.
Может состоять из одной детали или из многих, и может содержать **собственное пространство**:

```
COMPONENT  Ящик #12   (TYPE = ящик)
├── PART   бок левый
├── PART   бок правый
├── PART   задняя стенка
├── PART   дно
├── PART   фасад
└── SPACE  внутренний объём ящика
```

### E06 — PART
Одна физическая деталь, которая попадает в раскрой. Знает материал через слот, толщину, кромку и
свои стыки. **У детали ровно один хозяин** (Z01): другие могут ссылаться, но не владеть.

### E07 — TYPE
Рецепт: **что это за вид вещи и как она строится**. Тип существует на любом масштабе:

```
тип детали        полка · боковина · перегородка · фасад · задняя стенка
тип компонента    ящик · дверь · ручка · корзина
тип юнита         нижний · верхний · пенал · антресоль
```

**У типа есть домен** (Q87): тип — это `{ домен, имя }`, и типы разных доменов несравнимы:
`{PART, полка}` и `{UNIT, пенал}` — разные вещи.

**Тип объявляет параметры, экземпляр хранит их значения** (Q88):
```
TYPE {COMPONENT, ящик}        COMPONENT Ящик #12
параметры:                     значения:
  делений по x  (1…12)           делений по x = 6
  делений по z  (1…8)            делений по z = 4
```
Поэтому «носочница 6×4» — это **не отдельный тип**, а тип «ящик» с параметрами. Каталог не
распухает от комбинаций.

Тип хранит состав, правила, параметры и значения по умолчанию — **но не готовые миллиметры**.
Размеры появляются только у конкретного компонента в конкретном пространстве и профиле (Z08).

**Правила профиля висят на типе детали:** у типа «полка» — отступ спереди, зазор сзади, кромка,
способ стыка. Поэтому отдельное слово «роль» больше не нужно.

### E08 — PATTERN
Повторение одного компонента по правилу: **один тип × N вдоль одной оси × распределение**.

```
SPACE 688 высотой
└── PATTERN  полка × 5,  1:1:1:1:1,  ось Y

     ┌──────────────┐
     │   SPACE      │   ← промежутки настоящие: сюда можно ставить
     ├──────────────┤  полка (компонент паттерна)
     │   SPACE      │
     ├──────────────┤  полка
     │   SPACE      │
     ├──────────────┤  полка
     │   SPACE      │
     ├──────────────┤  полка
     │   SPACE      │
     └──────────────┘
```

**У каждого промежутка свой uid** (Q89): промежуток — это обычное пространство `S12`, и вещь в нём
привязана к нему, а не к «третьему снизу». При смене количества промежутки сопоставляются по
порядку, исчезающий должен быть пуст ([16_RUNTIME](16_RUNTIME.md) R03, R04).

**Промежутки живого паттерна — настоящие пространства** (Q67): в средний можно поставить ящик, не
распуская паттерн. Безопасность держится на трёх правилах (Z03):
1. любая правка паттерна сначала пересчитывает промежутки и проверяет, что в них стоит;
2. не помещается — **отказ целиком, граф не изменён**, названо то, что мешает;
3. предмет в промежутке привязан к граням соседних полок ссылкой, а не числом.

### E09 — ОТВЯЗАТЬ ОДИН и RELEASE
Два разных действия.

**Отвязать один** — мастер опустил одну полку. Паттерн делится на два, каждый со своими долями:

```
до                                после «отвязать полку 3»
PATTERN 5 полок 1:1:1:1:1         PATTERN A  полки 1, 2   (1:1)
                                  полка 3 — самостоятельная
                                  PATTERN B  полки 4, 5   (1:1)
```

Остальные полки **не двигаются** и остаются параметрическими (Z04).

**RELEASE** — **конец параметрического управления**, а не «размеры навсегда» (Q91): дальше размеры
ещё правятся вручную, а стыки добавляют производственную геометрию, не трогая размер в модели
(Q92). Все компоненты становятся самостоятельными, каждый со своим размером и положением. Новой сущности не появляется, меняется
только состояние управления (Z05). После RELEASE изменение габарита юнита компоненты **не двигает**
(Q69). Нужны доли обратно — создайте паттерн заново.

Происхождение остаётся в журнале команд: undo возвращает паттерн.

### E10 — GROUP
Произвольная пользовательская группа, как в Photoshop: двигать, прятать, копировать, менять вместе.

```
GROUP «дверь в сборе»        GROUP «фасады слева»
├── COMPONENT дверь          ├── COMPONENT дверь #1
├── COMPONENT ручка          ├── COMPONENT дверь #2
└── COMPONENT планка         └── COMPONENT дверь #3
```

Группа **не несёт конструктивного смысла** (Z10) и работает во всех трёх приложениях.

### E11 — SCOPE
**Не сущность**, а список «применить к…», который есть у каждого изменения:

```
Сменить кромку
применить к →  ○ этой детали
               ○ этому компоненту
               ● всем деталям типа «полка» в этом юните
               ○ этой группе
               ○ всему юниту
```

Изменение применяется **один раз и записывается** (Q75). Живых правил, которые срабатывают потом
сами, нет: это прямое следствие принципа «ничего автоматически».

### E12 — SLOT
Именованное общее значение проекта: `ФАСАД-A`, `ФАСАД-B`, `КОРПУС-A`, `КРОМКА-A`.

```
ФАСАД-A = белый глянец      двери низа   → ФАСАД-A
ФАСАД-B = дуб               двери верха  → ФАСАД-B
```
Поменяли слот — поменялось всё, что на него ссылается. Слот — это переменная, а не материал.

### E13 — КАТАЛОГ
Каталог — **место, где лежат типы**. Отдельных слов «образец» и «копия» в ядре нет (Q95): то, что
лежит в каталоге, — это **тип с параметрами по умолчанию**, а то, что стоит в проекте, — обычный
**компонент**. Поведение прежнее: правка типа меняет сделанные из него вещи, «сохранить как»
создаёт новый тип и рвёт связь (Q74).

Каталог, четыре уровня (Q84):
```
Компоненты  →  Юниты  →  Модули  →  Наборы
  витрина      витрина    мои         стиль
                          сохранённые целиком
```

### E14 — JOINT
Конкретный стык **в конкретной точке**: способ соединения, зазоры, отверстия и **кто проходит
насквозь**. Одна полка может иметь разные решения в разных местах (Z06):

```
   перегородка A    перегородка B    перегородка C
        │                │                │
────────┼────────────────┴────────────────┼────────  полка
   через: полка     через: перегородка   через: полка
   (полка целая)    (полка разрезана)    (полка целая)
```

**У каждого стыка свой uid** (Q93): полка и три перегородки дают три стыка `J1`, `J2`, `J3`.
Способ приходит из профиля как умолчание, любой стык меняется на месте, и это видно.

Способы соединения — **файлы настроек с картинками** (`things/joints/…/def.json` + `diagram.svg`).
Мастер выбирает способ по умолчанию один раз в профиле, а любой конкретный стык меняет отдельно (Z07).

### E15 — Режим стыков
После RELEASE мастер проходит по стыкам:

```
┌───────────────────────────────────────────────┐
│  ←   стык 7 из 24   →                          │
│                                                │
│   боковина ── полка                            │
│   способ: конфирмат 7×50                       │
│   через: боковина                              │
│   зазор: 0   отверстий: 2   шаг: 32            │
│                                                │
│   [сменить способ] [кто насквозь] [добавить]   │
└───────────────────────────────────────────────┘
```
Детали полупрозрачные, стык виден отдельно, стрелками по очереди. Клик по стыку — то же самое.

### E16 — MOTION
Ось, точка поворота, пределы, состояния, блокировки. Паспорт фурнитуры даёт значения по умолчанию,
но **нестандартное движение мастер объявляет сам** (Q81): самодельный откидной фасад — это ось и
угол 0–95°, а программа считает столкновения. За реальный механизм отвечает мастер.

### E17 — PROFILE и OVERRIDE
**Профиль** — нормы цеха: материалы, толщины, кромки, способы стыков, фурнитура, минимальные размеры.
**Override** — явное исключение на конкретной вещи, всегда видимое и считаемое: «1 переопределение».

## 4. Владение строгое, связи — граф

```
ВЛАДЕНИЕ (дерево, у каждой детали один хозяин)
SET → MODULE → UNIT → SPACE → COMPONENT → PART

СВЯЗИ (граф, сколько угодно ссылок)
полка ←→ боковина A        ручка ←→ фасад
      ←→ боковина B        петля ←→ фасад и боковина
общая боковина ← юнит A, юнит B (ссылаются, владеет модуль)
```

Это разрешает общую боковину без двух хозяев: **владеет модуль, юниты ссылаются** (Q64).
В App 2 общая деталь показывается как чужая, только для чтения.

## 5. Откуда берётся значение

Два слоя, а не одна лестница (Q96):

```
ЗНАЧЕНИЕ ПО УМОЛЧАНИЮ            ПРИМЕНЁННЫЕ ИЗМЕНЕНИЯ
профиль цеха → тип        +      команды мастера по порядку
                                 (кому применить — выбрал SCOPE или GROUP)

итог = умолчание + последнее изменение этого свойства
```

**У группы и scope нет «силы»**: они только выбирают цели. Побеждает не уровень, а **порядок
команд**, и в отчёте всегда видно, какая команда дала это число ([16_RUNTIME](16_RUNTIME.md) R53).

## 6. Разобранные примеры

**Носочница 6×4.** Нового примитива нет:
```
COMPONENT ящик  (TYPE = ящик)
└── SPACE внутри ящика
    ├── PATTERN перегородка × 6 по x
    └── PATTERN перегородка × 4 по z
```
Нужна 4×3 — меняются числа паттерна. Понравилось — сохранил образцом.

**Два цвета фасадов.** Один тип «дверь», два слота:
```
ФАСАД-A = белый → двери верхних юнитов
ФАСАД-B = дуб   → двери нижних юнитов
одна дверь зелёная → OVERRIDE на компоненте
```

**Три секции с общими боковинами.** Это модуль App 1 с общими деталями (§3 E02).

**Пять полок и ящик в середине.** Промежутки паттерна — настоящие пространства: ящик ставится
сразу. Попытка сменить 5 → 6 полок, когда ящик не влезет, — отказ с именем ящика.

**Смешанный ряд** «дверь, дверь, ниша, дверь, ящик» — несколько паттернов и отдельные компоненты
(Q71). Паттерн повторяет одинаковое, он не «строка разметки».

## 8. Чем отличаются похожие вещи

| | |
|---|---|
| **MODULE и GROUP** | модуль — общая конструкция; группа — совместное управление |
| **UNIT и MODULE** | юнит — одна ячейка; модуль — несколько юнитов с общими деталями |
| **TYPE и COMPONENT** | тип — рецепт; компонент — конкретная вещь |
| **COMPONENT и PART** | компонент — смысловой объект; деталь — физическая плита |
| **PATTERN и GROUP** | паттерн создаёт повторение; группа объединяет уже созданное |
| **SCOPE и GROUP** | scope — куда применить сейчас; группа — постоянный набор объектов |

## 9. Законы ядра

| id | Закон |
|---|---|
| **Z01** | У детали ровно один хозяин. Остальные ссылаются |
| **Z02** | Всё или ничего: конфликт → отказ, граф не изменён |
| **Z03** | Паттерн не ломает чужое: перед правкой проверяет всё, что стоит в промежутках |
| **Z04** | Отвязка одного не разрушает остальных: паттерн делится на два |
| **Z05** | RELEASE не создаёт новой сущности, меняет только состояние управления |
| **Z06** | Стык локален: у каждого пересечения своё решение |
| **Z07** | Любой стык мастер может изменить; значение по умолчанию не запрещает местное решение |
| **Z08** | Тип — рецепт, а не готовые миллиметры: геометрия появляется у экземпляра |
| **Z09** | Модуль не создаётся сам: экономию показываем, решает мастер |
| **Z10** | Группа не несёт конструктивного смысла |
| **Z11** | Профиль даёт значения по умолчанию; переопределение всегда видно |
| **Z12** | Нестандартное разрешено: если мастер может описать геометрию, связь, движение и производство существующим языком, система обязана это позволить |
