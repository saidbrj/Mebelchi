Jihozla — что где лежит и кто за что отвечает

Приложение — это монорепозиторий. Продукт живёт в apps/app и построен вокруг маршрута из 7 шагов: от рисования комнаты до передачи на производство. Эта карта показывает, какие файлы относятся к каждому шагу, и как разделить работу между тремя людьми.

Стек: React + Vite + Capacitor (iOS/Android) Состояние: Zustand (store.ts) 3D: Three.js Данные: Supabase + localStorage
?

Можно ли делить работу по папкам? — Да, по фазам маршрута. Приложение уже разложено по слоям (экраны / компоненты / 3D / модель), это хорошая база. Но три вещи заставляют всех трогать одни и те же файлы: общий store.ts, дублирующиеся движки раскладки и 3D, и общее «ядро» model/. Поэтому делим по фазам + держим три правила (внизу страницы).

03

Общее ядро — трогать только по согласованию

Эти файлы использует каждая фаза. Ни за одним человеком они не закреплены — правки маленькие и через ревью.

⚠ Не редактировать в одиночку

store.ts — «мозг» приложения на ≈2470 строк, импортит ~30 файлов модели. Здесь чаще всего случаются конфликты слияния. styles.css — общие стили. model/ и packages/schema — контракт данных: изменение может сломать чужую фазу.

04

Слои внутри apps/app/src

Правило зависимостей: экраны → компоненты → 3D / модель. Модель — чистая логика, без React и Three.

main.tsx → App.tsx
Точка входа и роутер. Это switch по store.screen (не react-router). Порядок шагов — в FLOW внутри store.
store.ts
Единый Zustand-store: всё состояние и все действия. Общий центр.
screens/
По одному файлу на шаг маршрута — верхнеуровневые фичи.
components/
Переиспользуемый UI + большие редакторы (конструктор, чертежи).
three/
Весь рендеринг на Three.js.
model/
Чистая доменная логика: геометрия, солвер раскладок, ЧПУ, DXF, тарифы. Без UI. ≈38 файлов.
lib/
Инфраструктура: Supabase, облачная синхронизация, шаринг файлов, превью.
i18n/
Словари ru/uz + хук useT().

06

Три правила, чтобы ничего не ломалось

Делим по фазам — и держим эти договорённости, пока не проведём рефакторинг store и не уберём дубли движков.

1

store.ts и styles.css — общие

Меняем по согласованию, маленькими правками, ревьюим диффы именно по этим двум файлам. Позже разрежем store на слайсы по фазам.

2

Не плодим дубли движков

Не добавляем 4-й движок раскладки и 3-й 3D-рендерер. Расширяем существующий под свою фазу — иначе «как выглядит шкаф» окажется в трёх местах.

3

model/ и schema — это контракт

Изменение в общей модели может сломать чужую фазу. Всегда помечай такие правки в ревью и предупреждай команду.

Карта отражает состояние репозитория на момент составления. Крупные файлы (VariantScene ≈3345, store ≈2470, ConfigScreen ≈1652) — кандидаты на разбиение: это самый быстрый способ сделать деление по папкам по-настоящему независимым.
