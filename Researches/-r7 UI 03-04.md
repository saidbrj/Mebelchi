# 3) `storage_object_classes` (the object-by-object table you asked for)

## Load model used (because most dimension standards don’t prescribe “expected shelf load”)

To keep this machine-usable _and_ standards-based, the `expected_load_kg_per_m_*` fields below are computed from the **EN 14749 overload UDL test loads** (kg/m²) quoted in a conformity test report (it explicitly references **EN 14749:2016+A1:2022 §5.3.11.3**). [7](https://device.report/m/aea5cb569c08c0773501ced721fb369029b0d6a2a528cfd919b0bb4e4c5a6d47.pdf)

**UDL levels (kg/m²):**

- bottom: 250
- 1st shelf: 150
- 2nd shelf: 100
- 3rd+ shelves: 65
- top: 50 [7](https://device.report/m/aea5cb569c08c0773501ced721fb369029b0d6a2a528cfd919b0bb4e4c5a6d47.pdf)

**Conversion used (explicit in each row):**  
`kg_per_m = kg_per_m2 * (depth_mm / 1000)`

This is not “what people will store”, but it’s a **standardized engineering/design load basis** you can consistently apply in rules.

## Practical integration tip (so this becomes a working `ergonomics_rules.json`)

A robust way to implement this in software is:

1. Treat **object dimensions** (depth/clearance) as “hard constraints” from **ГОСТ 13025.1-85 tables** where available.
2. Treat **mount heights** as “soft constraints” with:

## Attack 3 — EN 14749 test loads used as design loads: this check will never fire

Document 76 builds its entire load model on EN 14749 certification UDL test loads: 250 / 150 / 100 / 65 / 50 kg/m² by shelf position. The document derives shelf design loads directly from these: for plates, `kg_per_m = 100 * depth_mm/1000`, giving 22–46 kg/running metre depending on depth.

EN 14749 is the European standard for testing strength and durability of storage furniture. The UDL tiers are the forces a shelf must survive during structural certification — overload test conditions, not service loads. The standard explicitly certifies survival under these loads, not that users are expected to load shelves to these levels.

The practical consequence: a kitchen cabinet shelf holding a full set of plates, stacked 10 high, at 3.5 kg per stack, in a 600 mm deep cabinet weighs approximately 35–40 kg per running metre in a heavily loaded configuration. EN 14749's test load for a mid-height shelf is 100 kg/m². The software checks `actual_load ≤ 100 kg/m²`. This check passes for every realistic kitchen load with 60 kg/m² of headroom to spare. The structural warning never fires. It is permanently useless.

Document 75's empirical approach (plates: 25 kg/m typical, 40 kg/m max; cans: 60 kg/m typical, 80 kg/m max) is closer to correct as a design load basis, but it conflicts with Doc 76's EN 14749-derived values for the same object classes.

The correct use of EN 14749 in this system: not as a load value, but as a structural threshold. ## Attack 4 — Panel thickness is completely absent, and this is the first-build failure

Neither document contains any rule about panel thickness, and this is the single most common source of BOM errors in parametric cabinet software.

The ГОСТ 13025.1-85 minimum interior dimension for base cabinets is 460 mm. The document says this is an interior dimension. A workshop uses 18 mm furniture board as standard. ## The gem both documents missed

Neither document has a `severity` field. This is the constraint that governs what the software actually does with all this data.

When a shelf simultaneously violates a reach-zone rule, a load rule, and a minimum-clearance rule, the software surfaces whatever warning the implementing agent coded first. Without a severity tier, that will be the order the rules appear in the JSON — which means ergonomic warnings (interesting but safe) will surface before structural warnings (physical collapse risk). This is the wrong priority order for a tool used in manufacturing.

The correct three-tier severity for cabinet design software:

1. Structural risk — shelf load exceeds material capacity, span exceeds safe deflection limit. Physical failure, injury risk. Red, blocking.
2. Regulatory non-compliance — dimension falls below ГОСТ or EN minimum. Certification failure, returns from clients. Orange, blocking.
3. Ergonomic sub-optimal — outside preferred reach zone but above absolute minimum. Inconvenient, not unsafe. Yellow, advisory.

## (a) Detented / stepped drag

The cleanest working model is **Nomad Sculpt's gizmo**, because it separates _constrained_ from _free_ movement geometrically rather than modally. You drag the line-plus-arrow handle to move along a single axis, drag the peach dot in the center of the gizmo to translate freely in screen-space, and tap the colored squares to move in a plane. **Procreate** proves the inverse escape model. **Haptic conventions** are codified by Apple, and you should follow them rather than invent:

- UISelectionFeedbackGenerator is for a selection actively changing, such as picking an item from a list — this is the correct generator to fire _once per detent crossing_. It's the same light tick a Picker wheel gives.
- UIImpactFeedbackGenerator complements an action like a view sliding into place or two objects colliding — use this heavier "thud" when the line locks onto a hard constraint (a wall, another panel's edge), not for ordinary detents.
- UINotificationFeedbackGenerator is for a notification such as an action completing or failing — use only on commit/error, never during the drag.

## (d) Scope / target switching (one vs many)

Two proven approaches:

**Input-device routing (Concepts)** physically separates _what_ from _how_: you can set the finger to Select while the Apple Pencil keeps drawing, so you select with your finger and continue editing with the Pencil without switching tools. If your workshop users have a stylus, "finger picks scope, pencil applies the edit" is a strong, fatigue-free model.

**The selection set is the scope (Figma).** Once multiple objects are selected, they're wrapped in one bounding box and you edit them all at once. The expression of "one vs many" lives in the edit field itself: a shared value shows the number; differing values show a _mixed/placeholder_ state, and typing a value writes it to all. That mixed-value field is the cleanest way to say "you're about to change N panels."

For a cabinet editor, combine them: **scope = current selection; the numeric sheet carries an explicit "this panel / all N selected" affordance, and shows "—/Mixed" when selected parts differ.** Don't make scope implicit — that's where destructive accidents come from.

## (e) Accidental-edit prevention

The lessons converge on five rules, each with a proof point:

1. **Navigation gestures must never mutate geometry.** Shapr3D, Nomad, and Concepts all separate input streams so panning/orbiting can't edit. Nomad makes this explicit: a finger drag can be limited to move the camera while a stylus drag sculpts.
2. **Don't auto-commit on dwell.** Procreate's QuickShape is the anti-pattern — it auto-triggers on hold, and once snapped you can't undo back to the pre-snap line; you have to redraw from the start. Any auto-snap needs a cheap escape _and_ a recoverable undo.
3. **Numeric edits commit only on explicit confirm.** Shapr3D's tap-the-check-mark gate. You input the value, then tap the check mark to apply.
4. **Palm/finger rejection as a first-class setting.** Concepts offers a "Do nothing" finger action for extra-robust palm rejection.
5. **Undo always one gesture away.** Procreate's two-finger tap to undo is the most-internalized touch convention there is — adopt it verbatim.

# Recommended gesture spec

### 1. move-line-with-detents

**Gesture:** single-finger (or Pencil) drag on the line's body or an axis handle. Drag begins only after a small dead-zone (~8–10 pt) so a tap is never read as a micro-move. **Behavior:** snaps to a two-tier detent — fine 1 mm, coarse 32 mm — with the active detent value shown on-canvas and editable in place (Nomad model). **Escape to free:** drag past a velocity/distance threshold, _or_ grab a dedicated free-move handle, so detents never trap a deliberate fine adjustment. **Haptics:** `UISelectionFeedbackGenerator` tick per detent crossing; `UIImpactFeedbackGenerator` thud only when locking to a hard constraint (adjacent panel edge, carcass wall). **Proven by:** Nomad Sculpt gizmo (constrained-vs-free handle geometry + editable live snap value) — https://nomadsculpt.com/manual/tools ; haptic mapping per Apple HIG — https://developer.apple.com/design/human-interface-guidelines/playing-haptics

### 2. precise entry

## Opening verdict

The spec is a good iOS design doc for a Shapr3D-like app on iPad Pro. The product being built runs offline-first on budget Android in a workshop in Tashkent. Those are not the same thing, and the gap kills four of the five core claims before a line of code is written.

---

## Attack 1 — The haptic stack is iOS-only code on an Android target

The entire haptic specification — `UISelectionFeedbackGenerator`, `UIImpactFeedbackGenerator`, `UINotificationFeedbackGenerator` — is UIKit. It does not exist on Android. The Android equivalent is `View.performHapticFeedback(HapticFeedbackConstants.CLOCK_TICK)`, and on the hardware that actually runs in Uzbek workshops — Xiaomi Redmi Note series, Samsung Galaxy A-series, Tecno Spark — the LRA motors can distinguish "vibrate" from "no vibrate" but not three distinct impact weights. Flutter's `HapticFeedback.lightImpact()`, `.mediumImpact()`, and `.heavyImpact()` all call the same `Vibrator.vibrate()` with different duration parameters on low-end Android; the difference is imperceptible.

**The spec uses haptics as a primary communication channel for detent crossing.** On a meaningful percentage of target devices, those ticks fire as nothing. There is no fallback.

**Replacement:** Visual snap is the correct primary channel. When a drag crosses a detent, the dimension label _jumps_ — not smoothly animates, jumps — to the snapped value. This is hardware-agnostic, works with gloves, works in daylight. Haptics become a `try/catch` enhancement: attempt it, fail silently if unsupported. Google Maps uses visual card-lift for POI snapping on Android for exactly this reason.

**Survives:** The three-tier haptic _taxonomy_ (selection tick / impact thud / notification) is conceptually correct and should be preserved as the _intent_ specification, implemented against each platform's actual capabilities rather than UIKit APIs.

---

## Attack 2 — "Always-visible dimension labels" fails at stated scale

The spec calls Shapr3D's always-on dimension labels the "gold standard." Shapr3D shows dimensions for _one active sketch at a time_. The cabinet tool needs to render hundreds of panels simultaneously.

Scale reality check: a standard 20-cabinet kitchen has width + height + depth labels per panel. That's 60+ live text nodes in the resting state. Now add position dimensions. Now consider the user is zoomed out to see the full run. The labels are either: (a) readable size, covering all geometry and making the view unusable; (b) minimum readable but requiring zoom to read, defeating always-visible; or (c) auto-hidden below a zoom threshold — which means it's not "always-visible," it's zoom-conditional. There is no version of this that works.

**The technical cost is real.** Each visible label is a live reactive node that must recalculate position, value, and visibility every frame during drag. At 60 fps with 60 labels, that's 3,600 label-position calculations per second alongside geometry math, BOM lookups, and touch event processing. On a Mediatek Helio G85, this is measurable frame drop territory. AutoCAD Mobile and ArchiCAD BIMx hide dimension labels for non-selected geometry — not as a limitation, as a deliberate engineering decision made after shipping to exactly this scale.

**Replacement:** Labels appear only for the active (selected or being-dragged) element. All other panels: silent. This is not a degraded experience — users can only read one dimension at a time anyway. The always-visible framing was borrowed from a single-sketch editor and applied incorrectly to a full-layout editor.

---

## Attack 3 — The System-32 detent is a domain knowledge error

System-32 is a manufacturing assembly standard for the _spacing of 5mm shelf-pin holes, drawer-slide mounting holes, and hinge-plate bores_. The 32mm pitch is a drill-jig standard. It governs where you drill holes in a panel. It has no relationship to panel dimensions.

Standard European cabinet panel widths, from Häfele, Blum, and Grass hardware catalogs: 150, 200, 250, 300, 350, 400, 450, 500, 600mm. Every single one is a 50mm increment. A 32mm coarse detent applied to a 300mm panel produces nearest snaps of 288mm (9×32) and 320mm (10×32). Neither is a standard width. The detent would fight every common cabinet dimension in the field.

**The error would manifest as:** "my panel keeps snapping to 288mm instead of 300mm" — a bug report that reads like a snap-logic error because the system is working exactly as specified.

**Correction:** Fine detent 1mm. Coarse detent 50mm. These are the only values that land on real panel sizes.

---

## Attack 4 — Long-press for multi-select entry has documented failure modes

Flutter's gesture arena creates a disambiguation window between `LongPressGestureHandler` and `GestureDetector` during the hold period. On slower devices, the recognizer competition causes "stolen" gestures where long-press intent resolves as drag. This is a category of bug that is extremely hard to reproduce consistently and nearly impossible to explain to a user. Google's Material Design 3 (2022) explicitly moved away from long-press-to-select toward checkbox-mode entry for this reason — the announcement cites ambiguity with scroll and pan as the primary motivation.

Add the physical context: workshop users have rough hands. Slight callus or tremor creates micro-wobble during a 500ms stationary hold that reads as drag initiation, canceling the multi-select intent. The failure mode is "sometimes dragging doesn't work" — a complaint that will never generate a reproducible bug report.

**Replacement:** Persistent multi-select toggle button in the toolbar. One tap enters mode; every subsequent tap toggles membership; second tap on the button exits. This is how iOS Files.app, Google Photos, and every mature file manager solves the same problem. The mode state is visible (button highlighted), there is zero gesture ambiguity, and it works with rough hands.

**What survives from the original:** dim non-selected elements during multi-select (correct, keep it), marquee from empty canvas (correct, keep it).

---

## Attack 5 — The Procreate model has inverted polarity

The spec cites Procreate's "second finger to constrain to 15° increments" as proof for how to escape a detent. The analogy is backwards.

Procreate's model: free movement → _add_ constraint (second finger adds snap). Default is freehand. Constraint is intentional. This is correct for an art app where freehand is primary.

For manufacturing software: the desired model is constrained (detented) by default → _escape_ to free for fine adjustment. This is opposite polarity.

The correct proof-app is digital audio workstations. In Ableton Live, dragging a clip snaps to the grid by default; holding Cmd/Ctrl disables the grid for sub-grid positioning. Same in Logic Pro's piano roll. The "hold modifier to escape constraint" pattern is well-established in precision creative tools, and its touch translation is: hold a second finger on any neutral area of the screen while dragging with the primary finger to disable detents. Structurally identical to Procreate but with the correct polarity for a tool where constrained is the safe default.

---

## Attack 6 — The "Mixed" field is a desktop-only interaction

The Figma-derived "Mixed" placeholder behavior assumes: select-all with Cmd+A, then type to replace. On mobile touch keyboards this doesn't exist. The user must manually tap-select inside the field before typing, which requires precision touch on a small number. Across Samsung, MIUI, and OxygenOS keyboards, placeholder vs empty-field focus handling is inconsistent — a category of bug that only surfaces on devices you don't test on.

**Replacement:** When entering numeric edit with multiple panels selected, a modal sheet appears: "Set [dimension] for [N] selected panels → [input field] → Cancel / Apply." The N-count makes scope explicit before commitment. The same pattern used by iOS Mail and Files for bulk editing. This also eliminates the silent partial-edit failure mode where the field commits to one panel instead of all.

## What survived the attack

These pass unchanged:

- **8–10pt dead-zone before drag activates.** Correct. Keep it.
- **Explicit ✓ to commit numeric entry.** Critical for manufacturing — a mis-committed value means wrong cut dimensions and wasted material. Keep without modification.
- **Marquee from empty canvas, drag from object.** Correct disambiguation rule. Keep it.
- **Expression support in the numpad** (`720-2*18`). Actually the most important feature in the entire spec for workshop use, and it was underemphasized. Operators calculate dado depths and rabbet widths mentally and want to enter them as math. Keep and surface it prominently.
- **Two-tier detent concept** (fine/coarse). Valid architecture. Wrong values: corrected to 1mm / 50mm above.
- **Tap label → numpad opens.** Correct direction. Priority inverted by the gem below.

## The gem the original missed

The entire spec was designed for the wrong primary user. It optimized for a designer _exploring_ proportions — dragging a panel to see how 300mm looks, then refining. The actual user is a workshop operator with a cut list who knows they need 300mm because the room is 600mm and they're placing two equal-width cabinets. They do not drag to discover dimensions. They already have the dimensions.

**The correct priority order is inverted: type first, drag second.**

First tap on any panel should open the numpad immediately. Not: tap → see label appear → tap label → numpad. One gesture, not two. Drag is a coarse layout tool that snaps to the 50mm grid only — it is physically incapable of producing precision results, and that is correct behavior. All precision flows through the numpad. Design the selected-panel affordance to make this path unmissable: a large, clearly tappable dimension chip, not a small sketch annotation that looks like read-only display.

The failure the original walks into: users drag a panel to "approximately right" and get 298mm instead of 300mm. They adjust via numpad. The numpad corrects it. Nobody files a bug. But the user has learned that the tool is imprecise and requires correction after every gesture. That erodes trust faster than any single bug.

The tools that get this right: Cabinet Vision (industry-dominant software, type-first throughout), Planit! Kitchen (opens dimension panel on first tap). Every tool built for _manufacturing_ rather than _exploration_ defaults to numeric entry. The original spec cited only exploration tools.
