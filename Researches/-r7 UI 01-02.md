### 1.1 БАЗИС-Мебельщик / БАЗИС-Шкаф (Bazis-Mebelschik / Bazis-Shkaf)

**Developer:** ООО Базис-Центр (Russia) **Platform:** Proprietary (Windows), own 3D math kernel

#### (a) Core Structural Model

[1](https://bazis-center.ru/system/mebelschik) БАЗИС-Мебельщик is the main module of the БАЗИС system, designed to create case-furniture products of any complexity, with automatic generation of a complete set of drawings and specifications. [6](https://dtf.ru/software/5035106-bazis-mebelshchik-proektirovanie-korpusnoy-mebeli) It is a professional module for designing cabinet furniture, building 3D product models, preparing drawings and specifications, and transferring data to production modules. The program is oriented not to abstract 3D modeling, but to real furniture production tasks: wardrobes, kitchens, dressers, shelving, trade equipment, walk-in closets, sectional constructions, and custom non-standard items.

The БАЗИС system uses two structurally distinct modules:

- **БАЗИС-Мебельщик** — a full 3D assembly modeler. [3](https://cdn.bazissoft.ru/documentation/ru/Bazis.pdf)Its auxiliary panel explicitly exposes a **«Структура модели»** (Model Structure) panel — a hierarchical tree that mirrors the parametric assembly structure. The tree nests as: **Проект (Project) → Изделие (Product/Article) → Секция (Section) → Деталь (Part/Panel)**. Dimensions are stored as parametric expressions; "Свойства" (Properties) are per-node attributes. [3](https://cdn.bazissoft.ru/documentation/ru/Bazis.pdf)An "История" (History) panel records operation sequence, while "Свойства" (Properties) stores per-element attributes — analogous to a feature tree.
    
- **БАЗИС-Шкаф** — a wizard-driven "wardrobe" specialized sub-tool. [2](https://www.bazissoft.ru/products/bazis_shkaf/doc-bsh)Its documentation covers: the cabinet design wizard (Мастер проектирования), door design wizard, drawer design wizard, materials database, and library/project management. Шкаф operates with a **секция (section)** model: a wardrobe is decomposed vertically into **секции (sections)**, each bounded by **боковины (side panels)**, **полки (shelves)**, and **перегородки (dividers/partitions)**. Each секция can have its own door treatment, internal fittings, and height.

#### (b) Dimension Edit Propagation

[6](https://dtf.ru/software/5035106-bazis-mebelshchik-proektirovanie-korpusnoy-mebeli) The principal feature of БАЗИС-Мебельщик is the direct link between the geometry of the model and production data. Dimension changes are parametric: editing an overall carcass dimension (e.g., cabinet width) propagates down to all child panels whose expressions reference it. The scope is controlled by:

- **Изделие-level edit:** Changing габариты (overall dimensions) in the Свойства panel propagates to all sub-panels whose formulas reference that parameter — effectively a **global** scope within one article.
- **Секция-level edit (БАЗИС-Шкаф):** Each section can have its own width; changing a section width redistributes only the panels within that section (**local/group scope**).
- **Деталь-level edit:** Overriding an individual panel's dimension breaks the formula link, making it a **local** override independent of parent changes.

[6](https://dtf.ru/software/5035106-bazis-mebelshchik-proektirovanie-korpusnoy-mebeli) The software conveniently supports creating standard furniture modules, using libraries, fragments, parametric elements, repeating sections, and configured templates.

#### (c) Alignment / Symmetry / Equal-Spacing

БАЗИС-Мебельщик provides:

- **Равномерное распределение (Equal distribution):** Multiple dividers can be placed by specifying count; the system calculates equal spacing automatically.
- **Симметрия (Symmetry):** Mirror operations are accessible for symmetric compositions (e.g., symmetric door pairs, symmetric shelf arrangements).
- **Выравнивание (Alignment):** Standard alignment commands are available in the 2D drawing editor component.

(Source: synthesized from БАЗИС user manual table of contents indicating section "Основные приемы работы" / basic operations.)

#### (d) Adding / Removing Shelves and Dividers

In **БАЗИС-Мебельщик:**

- **Insert:** A shelf or divider is inserted into an existing секция by specifying its position (absolute mm from datum, or as a formula/percentage). The system recalculates adjacent void spaces.
- **Split:** A секция is split by inserting a перегородка (vertical divider), which creates two child zones each inheriting the parent's height.
- **Delete:** Removing a перегородка merges the two adjoining sections back; removing a shelf collapses the two shelf zones.

In **БАЗИС-Шкаф:**

- The wizard allows specifying the number of sections and their widths upfront; sections can be added/removed post-creation via the section editor dialog.

#### (e) Rows of Furniture (Base / Upper / Tall)

[6](https://dtf.ru/software/5035106-bazis-mebelshchik-proektirovanie-korpusnoy-mebeli) БАЗИС covers kitchens, wardrobes, dressers, shelving, and sectional constructions. Rows are handled as **independent Изделия (articles)** placed in a **Проект (Project)** room scene. There is no hard "row" abstraction — base cabinets (нижние тумбы), upper cabinets (верхние шкафы), and tall units (высокие шкафы) are separate assembly objects positioned in 3D space. [6](https://dtf.ru/software/5035106-bazis-mebelshchik-proektirovanie-korpusnoy-mebeli) When a company produces kitchen lines, wardrobes, or office furniture, reuse of structural solutions reduces design time; repeating sections and configured templates are the primary mechanism.

### 1.2 imos iX (imos AG, Germany)

**Developer:** imos AG (Germany) **Platform:** AutoCAD-based (iX CAD AC) or standalone (iX CAD)

#### (a) Core Structural Model

[12](https://www.imos3d.com/en/products/design-order/) imos's database technology is based on an object-oriented approach. Components such as sides, floors, and doors, or entire assemblies, are in a direct constructive relationship with each other. Variable in dimension and material composition, all properties that affect the design process — material, surface, edges, drilling patterns, fittings, and connection situations — are already defined and automatically taken into account.

The structural hierarchy in imos iX is: **Room → Article (Artikel) → Zone (Zone) → Single Part (Einzelteil)**. The **Article Designer** is the primary structural tool:

[11](https://www.imos3d.com/en/products/design-order/ix-cad-1/) The Article Designer is ideal for variable-size constructions, covering requirements in cabinet and object construction when similar furniture with different dimensions or front divisions is required. It accesses parametric components. [11](https://www.imos3d.com/en/products/design-order/ix-cad-1/) In the Object Designer, components are generated via 2D top-view and side-view drawings; the 2D geometry data can be created using simple functions such as polyline. iX CAD automatically generates the complete 3D element with all details from the various 2D views. By changing the 2D drawing elements, the 3D model can be adjusted with a mouse click.

The **Element Manager** organizes structural "Construction Principles":

[16](https://support.imos3d.com/fileadmin/imosOnlineHelp/iX2017/ENG/Content/Resources/Topics/Whats_New/WhatsNew_CAD_EM.htm) The Drawer Manager has been integrated in the Element Manager as "Drawers," assigned to the Construction Principles, located below Single Parts in the hierarchy. [16](https://support.imos3d.com/fileadmin/imosOnlineHelp/iX2017/ENG/Content/Resources/Topics/Whats_New/WhatsNew_CAD_EM.htm) Annotation Principles are located below "Output" in the Element Manager, enabling object-related and conditions-based annotation principles.

The Zone concept in Article Designer: [16](https://support.imos3d.com/fileadmin/imosOnlineHelp/iX2017/ENG/Content/Resources/Topics/Whats_New/WhatsNew_CAD_EM.htm)It is possible to define different sub-articles depending on the height of the article via Descriptors accessed in the Article zone by right-clicking. If the descriptor of the type "Article" defined beforehand is selected, the article suitable for the current height will always be inserted in the zone.

#### (b) Dimension Edit Propagation

[11](https://www.imos3d.com/en/products/design-order/ix-cad-1/) The integrated data model typical of imos iX offers the greatest possible security, even when changing and updating data.

imos uses **parametric formula-based dimensions** linked to article parameters. Scope control:

- **Article-level (global):** Changing the article's overall dimensions (width/height/depth) propagates through all construction principles and sub-articles referencing those parameters.
- **Zone-level (group):** Each zone within an article can have its own dimensional descriptor; editing a zone parameter affects only components within that zone.
- **Part-level (local):** Individual Single Parts can have locally overridden formulas.

[16](https://support.imos3d.com/fileadmin/imosOnlineHelp/iX2017/ENG/Content/Resources/Topics/Whats_New/WhatsNew_CAD_EM.htm) It is possible to create descriptors of the type "Construction Principle," selecting from all Construction Principles and Articles. If Article is selected as the construction principle, different sub-articles can be defined depending on the height of the article. [16](https://support.imos3d.com/fileadmin/imosOnlineHelp/iX2017/ENG/Content/Resources/Topics/Whats_New/WhatsNew_CAD_EM.htm) In the Element Manager, it is possible to duplicate entries — for example, duplicate a row in the dimensioning principles (the same row inserted again in the same principle). With "Copy row," the same row can be inserted into a different dimensioning principle.

#### (c) Alignment / Symmetry / Equal-Spacing

imos iX handles this through **Construction Principles** — rule-sets that define repetitive elements. Equal-spacing of shelves or front divisions is expressed as a formula distributing the zone height/width evenly among N parts. The Article Designer supports:

- **Symmetry axis** in 2D profile drawing, which imos maps to 3D.
- **Equal distribution** via formulas in dimensioning principles.
- [11](https://www.imos3d.com/en/products/design-order/ix-cad-1/) The Article Designer specifically covers requirements when "similar furniture with different dimensions or front divisions is required," implying systematic division control.

#### (d) Adding / Removing Shelves and Dividers

[17](https://imos-ix-cad.software.informer.com/) Designers configure catalog-driven components, apply materials and hardware from libraries.

- **Insert:** A new Single Part is added to a Zone via the Element Manager; its position is specified by a formula or by placement mode.
- **Split:** A Zone can be subdivided by adding a divider, creating sub-zones. The parent zone height/width is distributed.
- **Delete:** Removing a part from the construction principle re-merges the zone.
- [16](https://support.imos3d.com/fileadmin/imosOnlineHelp/iX2017/ENG/Content/Resources/Topics/Whats_New/WhatsNew_CAD_EM.htm) It is possible to copy entire sections — enabling rapid duplication of divider/shelf groups.

#### (e) Rows of Furniture

[14](https://www.imos3d.com/en/) iX Interio digitizes processes from planning and sales, order entry and design to production organization, manufacturing, and assembly. Base/upper/tall cabinet rows are managed at the Room Planning level — each article is independently positioned and sized, but they share the same Article/Zone/Part data model. [11](https://www.imos3d.com/en/products/design-order/ix-cad-1/) Long parts such as countertops, baseboards, light mouldings, and crown mouldings can be generated based on the room situation and scheduled items, executed to fit the order in the factory — illustrating how inter-row elements are handled as room-contextual items.

### 1.3 PolyBoard (Boole & Partners, France/Belgium)

**Developer:** Boole & Partners **Platform:** Windows standalone

#### (a) Core Structural Model

[23](http://fittingsoftware.com.au/polyboard.htm) PolyBoard uses the **'zone' or 'cells' system** where you can select any area within the cabinet and access the drop-down menu, allowing you to easily add cabinet components including shelves, dividing panels, doors, and drawers.

The hierarchy is: **Project → Cabinet → Inner Volume (Zone/Cell) → Panel Part**. The cabinet is initialized as a bounding box; internal zones are created by adding shelves (horizontal) or uprights (vertical), which split existing zones recursively. [22](https://wooddesigner.org/help-centre/polyboard-cabinet-mode/)Because PolyBoard is parametric, you can very quickly define irregular angles and slopes and PolyBoard instantly creates a coherent design.

**External Zones** are a distinct structural category:

[28](https://wooddesigner.org/face-frames-fillers-plinths-using-polyboard/) External Zones allow you to add spaces (volumes) outside the main cabinet, to which you can add a range of structures. These zones can be applied to the top, bottom, back, and sides. [29](https://wooddesigner.org/polyboard-7-new-features/) In PolyBoard version 7, plinths and upper strips are added via a new External Zones section in the Properties menu. Completely new is the ability to create lateral zones around the cabinet, based on the sides and the back.

**Nil Panels** are a virtual structural device:

[21](https://wooddesigner.org/help-centre/polyboard-basic-design/) A nil panel is a virtual panel used to divide a volume where you don't want to add a real panel — a useful way to manage internal space, for example to add drawers above doors without a separating shelf.

**Position referencing** in v7: [29](https://wooddesigner.org/polyboard-7-new-features/)The reference position of an internal division may be set either as Zone (as in PolyBoard 6), or as one of the zone sides; the reference axis is illustrated by one or two red arrows.

#### (b) Dimension Edit Propagation

[25](https://wooddesigner.org/polyboard-software-tools/) PolyBoard offers fast and error-free parametric design — just type in the sizes and PolyBoard draws and updates your project automatically. [23](http://fittingsoftware.com.au/polyboard.htm) Overall cabinet dimensions are controlled and resized from the Properties dialog.

Scope:

- **Cabinet-level (global):** Changing overall W/H/D from the Properties dialog re-proportions all internal zones and parts.
- **Zone-level (group):** Each zone can have its position set as a fixed mm or proportionally; a proportional zone rescales when the cabinet is resized, while a fixed-distance zone holds its offset.
- **Part-level (local):** Individual parts can be overridden.

[28](https://wooddesigner.org/face-frames-fillers-plinths-using-polyboard/) If the dimensions of the project change, External Zone elements automatically resize and are updated in the manufacturing files. [21](https://wooddesigner.org/help-centre/polyboard-basic-design/) The Position of internal parts is defined proportionally within a volume or as a fixed distance from an adjacent panel — this is the user's choice of scope: **proportional = follows global resize; fixed = local override**.

#### (c) Alignment / Symmetry / Equal-Spacing

[24](https://polyboard.informer.com/) PolyBoard allows adding the number of slopes, adding vertical divisions, and modifying the distance between them.

- **Equal spacing:** Divisions can be distributed evenly by entering a count rather than absolute positions.
- **Symmetry:** Achieved via Manufacturing Methods sub-methods for "Dividing panels," which define default equal distribution rules.
- [21](https://wooddesigner.org/help-centre/polyboard-basic-design/) The "Individualize division parameters" command allows going one step further and editing individual façades rather than all of them at once — i.e., toggling between group-equal and individual-local mode.

#### (d) Adding / Removing Shelves and Dividers

[24](https://polyboard.informer.com/) Horizontal divisions (shelves) are allowed and can be fixed or mobile; the software permits adding doors and drawers into spaces.

- **Split:** Clicking inside a zone and selecting "Add shelf" or "Add upright" from the Quick Design Cabinets toolbar splits the zone. [27](https://wooddesigner.org/help-centre/polyboard-additional-design-features/)These are advanced shelves and uprights available from the Quick Design Cabinets toolbar (right-click or Modify menu); they can be placed at any angle to create anything from a functional shoe rack to a contemporary aesthetic.
- **Inner Casing:** [27](https://wooddesigner.org/help-centre/polyboard-additional-design-features/)With an inner volume selected, the inner casing feature creates two new inner volumes within the cabinet, which can each receive their own inner casing.
- **Part Split:** [23](http://fittingsoftware.com.au/polyboard.htm)The part split function divides parts into multiple parts to create cabinet rails, multi-part doors, or split panels — great for large parts.
- **Nil Panel deletion:** removing a nil panel re-merges the logical zones.
- [29](https://wooddesigner.org/polyboard-7-new-features/) Standard divisions and inner casings can be applied to the inner zones of drawers, making it possible to automatically create inner drawer separators.

#### (e) Rows of Furniture

[23](http://fittingsoftware.com.au/polyboard.htm) PolyBoard allows arranging cabinets in a 3D space representing a room such as a kitchen, office, or bedroom. Cabinets can be positioned using a simple drag-and-drop technique with automatic alignment with adjacent walls or cabinets.

Base/upper/tall rows are independent cabinet objects placed in the Project (multi-cabinet) mode. [29](https://wooddesigner.org/polyboard-7-new-features/)External Zones make it possible to add an extra panel to a cabinet side or to the side of two cabinets placed one on top of the other, without having to build it as a separate cabinet.

### 1.4 Cabinet Vision (Planit Solutions / Hexagon)

**Developer:** Planit Solutions (now Hexagon) **Platform:** Windows, AutoCAD-based

#### (a) Core Structural Model

[44](https://planitcanada.ca/wp-content/uploads/2022/04/The-Smart-Guide-to-Cabinet-Vision-Design-V20220405-1.pdf) Cabinet Vision works with a realistic 3D solid model of Parts, Assemblies, objects, and Rooms.

The structural hierarchy is: **Job → Room → Cabinet → Interior → Part**. The key concepts are:

- **Cabinet:** A parametric unit defined by W × H × D plus a **Construction Method** (frameless, face-frame, inset, etc.).
- **Interior:** The interior of a cabinet is a named structural container specifying the configuration of shelves, drawers, doors, and dividers. Interiors are pre-defined in the **Interior Library** and inserted into cabinets.
- **Opening / Section:** Within a multi-section cabinet, each vertical division creates an **Opening**, each of which may have its own door treatment and interior.
- **Part:** The lowest-level manufactured panel (Side, Bottom, Shelf, etc.) with full material/edge/machining properties.
- **Construction Method:** [44](https://planitcanada.ca/wp-content/uploads/2022/04/The-Smart-Guide-to-Cabinet-Vision-Design-V20220405-1.pdf)Cabinet Vision rolls out Construction Methods and sample Materials/Material Schedules; these define how the cabinet is structurally built and are required to be customized to the shop's own methods.

[45](https://mclinestudios.com/cabinet-vision-shop-drawings/) Cabinet Vision automatically generates cutlists and optimizes material usage; it seamlessly connects with CNC machines for accurate, automated production without manual data entry.

**Key vocabulary (EN):**

|Term|Meaning|
|---|---|
|Job|Project file|
|Room|Design environment|
|Cabinet|Individual furniture unit|
|Interior|Pre-defined internal configuration|
|Opening / Section|Vertical subdivision within a cabinet|
|Part|Individual panel/component|
|Construction Method|Global build rule-set (frameless, face-frame, etc.)|
|Material Schedule|Material assignment profile|
|S2M (Solid to Manufacturing)|Core production data pipeline|
|Screen-to-Machine|Marketing term for direct CNC connection|

#### (b) Dimension Edit Propagation

Cabinet Vision uses a **parametric cabinet engine**. Scope levels:

- **Job-level:** Global default sizes and Construction Methods apply to all new cabinets.
- **Cabinet-level (group):** Editing a cabinet's W/H/D resizes all its parts according to the Construction Method rules — if a shelf is defined as "full width minus 2× side thickness," changing cabinet width automatically updates shelf width.
- **Interior-level:** An interior can be swapped wholesale, changing all internal configurations at once.
- **Part-level (local):** Individual parts can be directly overridden in the Parts Editor, breaking the parametric link.

[31](https://sketchlist.com/blog/best-cabinet-design-software/) Cabinet Vision is the most complete production platform in its category, reflecting the depth of its parametric engine.

#### (c) Alignment / Symmetry / Equal-Spacing

Cabinet Vision handles this through Interior Library definitions:

- **Equal shelf spacing:** Specified by count; the interior engine divides available height evenly.
- **Symmetry:** Face-frame or door-pair symmetry is managed by the door configuration in the Interior definition.
- **Autofill:** [34](https://www.woodshopnews.com/features/next-level-design-software)Autofill functions quickly fill a space, a wall, or an entire room with library or custom cabinets.

#### (d) Adding / Removing Shelves and Dividers

- **Insert via Interior Editor:** Open the Interior Editor, click the zone, and insert a shelf, drawer bank, or vertical divider — the zone is split automatically.
- **Split Openings:** Adding a vertical divider in the Interior Editor creates additional Openings; each Opening inherits the cabinet height and can have its own door.
- **Delete:** Removing a shelf/divider in the Interior Editor re-merges adjacent zones.
- [34](https://www.woodshopnews.com/features/next-level-design-software) Users can add shelves, partitions, trays, and other items, shape individual parts as necessary, and create detailed product and part drawings.

#### (e) Rows of Furniture

Cabinet Vision explicitly distinguishes **Base**, **Upper**, and **Tall** cabinet types in its catalog. These are defined by different default height/depth parameters and different Construction Methods (e.g., base cabinets have toekick sub-construction; upper cabinets have hanging rail details). Multiple cabinet rows in the same room are independent parametric objects. [31](https://sketchlist.com/blog/best-cabinet-design-software/)Cabinet Vision has the strongest CNC integration, including direct machine code output for supported equipment.

### 1.6 PRO100 (IMSolutions)

**Developer:** IMSolutions (Poland, widely distributed in Russia/CIS and North America) **Platform:** Windows

#### (a) Core Structural Model

[34](https://www.woodshopnews.com/features/next-level-design-software) PRO100 is a 3D cabinet design software for cabinetmakers (frame or frameless), kitchen designers using stock cabinets, and shops building entertainment centers, closets, and garage cabinets. It can design and produce 3D renderings with dimensioned floor plans, room elevations, cut lists, cabinet lists, job costing, and pricing.

PRO100 uses an **object/element-based** model rather than a zone tree. The hierarchy is: **Project (Room) → Object (Object / Элемент) → Part (Element/Деталь)**. An "Object" is a free 3D box-shape that can be nested inside another — cabinets are built by composing box objects. There is no native zone concept; instead, division is achieved by placing shelf/divider box-objects inside a parent carcass object.

## 3. De-Facto Standard Operations (Present in 3+ Systems)

The following operations appear in **all 8 or most (≥3) systems** and constitute what a professional should expect as baseline functionality in any serious furniture CAD tool:

### Tier 1 — Universal (8/8 systems)

1. **Hierarchical assembly tree** — All systems organize a piece of furniture as a tree of named containers and leaf parts (even if the depth and terminology differ).
2. **Parametric or semi-parametric dimension editing** — At minimum, most systems offer some propagation of dimension changes from a parent container to child parts.
3. **Automatic cut list generation** — Every system in this comparison generates a cut/parts list from the 3D model automatically.
4. **Material library with thickness, grain, and edge properties** — All systems support material definitions that carry manufacturing properties.
5. **Alignment commands** — Standard left/right/top/bottom/center alignment of selected objects/panels.
6. **3D visualization** — All systems show a live 3D render of the design as it is built.

### Tier 2 — Near-Universal (7/8 systems, absent or weak only in PRO100 or SketchList)

7. **Zone / section / opening model** — A structural zone that contains components and can be subdivided. _Absent natively in PRO100 (pure object placement) and SketchList 3D (assembly/board only, no zone split)._
8. **Split zone by adding divider** — Clicking inside a zone and adding a shelf/upright creates two child zones. _Absent in PRO100; no zone concept in SketchList._
9. **Global dimension cascade** — Editing overall cabinet W/H/D updates all dependent parts. _PRO100 does not cascade automatically._
10. **Equal-spacing operation (count-based shelf placement)** — Specify N shelves; system calculates equal spacing. _PRO100 and SketchList require manual calculation._
11. **Construction Method / Manufacturing Method / Joinery Library** — A named rule-set that defines how a cabinet type is built, swappable globally. _PRO100 uses catalogue templates instead; SketchList is more basic._
12. **Base / upper / tall cabinet type distinctions in catalogue** — Separate catalogue entries or library sections for different furniture rows.
13. **Automatic hardware machining output (CNC drilling/grooving)** — Generated from hardware placement in the model. _Partial/optional in PRO100 and SketchList._

### Tier 3 — Majority (5–6/8 systems)

14. **Part-split function** — Dividing a single physical panel into two parts (useful for large panels, multi-material doors, rails). Present in БАЗИС, imos, PolyBoard, Cabinet Vision, Mozaik, W4I.
15. **External / lateral zone concept (plinths, strips, fillers)** — A zone outside the main carcass that carries structural elements. Native in PolyBoard (External Zones), Cabinet Vision (toekick sub-construction), W4I (sub-assembly), Mozaik; approximate in БАЗИС and imos.
16. **Symmetry axis operation** — Formal mirror/symmetry of internal divisions. Present in БАЗИС, imos, PolyBoard, Cabinet Vision, Mozaik, W4I.
17. **Local part-level dimension override** (breaking parametric link) — All systems allow this but the mechanism differs (formula override vs. direct edit).
18. **Structural link between furniture rows** — Updating one cabinet row also updating adjacent/related rows. Strong only in W4I (shared skeleton) and PolyBoard (External Zones spanning two cabinets); weakly supported in БАЗИС, imos, Cabinet Vision, Mozaik through room context.

### Tier 4 — Specialist / Advanced (3–4/8 systems)

19. **Nil / virtual panel** — A logical zero-thickness divider that separates zones without producing a real part. Native only in PolyBoard; approximate in imos and БАЗИС.
20. **Free / angled divisions** — Shelf or upright placed at an arbitrary angle. Native in PolyBoard (Free divisions), W4I (Inventor sketch geometry); partial in БАЗИС via custom geometry.
21. **Skeleton / multi-body parametric master** — A single driving geometry that controls all related parts across multiple assemblies. Only in W4I (Inventor multi-body skeleton) and partially in imos (Article Designer shared parameters).
22. **Descriptors / conditional sub-article insertion** — Inserting a different sub-article depending on a zone dimension. Native in imos iX Article Designer.
23. **Inner casing** — A recursive zone-within-zone container. Native in PolyBoard only.

## 4. Summary Observations

1. **Zone-based systems (PolyBoard, Cabinet Vision, imos, БАЗИС-Шкаф, Mozaik)** share the deepest structural editing vocabulary. A professional moving between them will find the concepts of zone/section/cell/opening directly analogous, even if named differently.
    
2. **Object-based systems (PRO100, early SketchList)** offer the lowest learning curve but the weakest parametric propagation. They are better presentation/sales tools than engineering tools.
    
3. **Assembly-based systems (W4I, SketchList 3D advanced, БАЗИС-Мебельщик)** are the most powerful for non-standard and complex furniture but require the highest expertise.
    
4. **The single most universal de-facto standard operation** is **automatic cut list generation directly from the structural model** — all 8 systems provide this, confirming it is the non-negotiable minimum for any professional furniture CAD tool.
    
5. **The most differentiating capability** is **the structural link between furniture rows** — only W4I (via skeleton) and PolyBoard (via External Zones) handle this at a deep structural level; all others treat rows as independent objects sharing only visual proximity in a room.
    
6. **Terminology varies significantly by region:** Russian-market tools (БАЗИС, PRO100) use терминологию (terminology) like _секция, деталь, перегородка, полка_, while Western tools use _zone, part, divider, shelf_. Despite different labels, the underlying abstractions (zone-split, divider insert, shelf add, equal-space) are structurally equivalent across the industry.

## 2) Per-system documentation (a)–(f)

### A) **Bazis — БАЗИС‑Мебельщик + БАЗИС‑Шкаф**

#### (a) Core structural model (hierarchy)

- **Мебельщик** exposes a **model tree** (“дерево модели”) as a **hierarchical** structure on the _Структура модели_ panel, synced with selection in the 3D scene. [24](https://s3-cold.bazissoft.ru/documentation/ru/Bazis.pdf)
- Мебельщик also tracks a **construction history** (История), enabling rollback to earlier steps and branching variants (the example explicitly shows a “horizontal panel/shelf” appearing/disappearing depending on the history state). [24](https://s3-cold.bazissoft.ru/documentation/ru/Bazis.pdf)
- In Bazis ecosystem terminology, “группа объектов” includes items such as **Блок, Сборка, Комплект сборок, Полуфабрикат или Секция** (used in the context of elastic sections). [25](https://rutube.ru/video/491d5260518a3ee78b6e242bc85732f0/)
- **Шкаф** uses an explicit **“section” (секция)** concept: a cabinet may consist of one or several sections, and each section is a part of interior space bounded (in front view) by fixed panels. [1](https://cdn.bazissoft.ru/documentation/ru/Cabinet.pdf)

#### (b) How a dimension edit propagates (scope + choosing scope)

- **Bazis‑Шкаф:** moving a panel (Сдвинуть панель) changes not only the panel position but also the **sizes/positions of elements of the section** it belongs to. [1](https://cdn.bazissoft.ru/documentation/ru/Cabinet.pdf)
- **Bazis‑Мебельщик:** elastic/parametric behavior is formalized via **“эластичность”**. The documentation describes _“параметрическая эластичная секция”_ and explains that when the containing section size changes, embedded sub-elements (example: drawers) also resize according to the defined algorithm. [24](https://s3-cold.bazissoft.ru/documentation/ru/Bazis.pdf)
- The elasticity model supports weighting different sub-sections so that different regions stretch by different amounts when overall cabinet dimensions change (described with “весовой коэффициент” and “в строгом соответствии с заданным алгоритмом”). [15](https://sapr.ru/article/24789)

#### (c) Alignment / symmetry / equal-spacing

- **Equal spacing by insertion count:** in Шкаф, if the user inserts more than one vertical panel (**N > 1**), panels are automatically placed at **equal distances** between section boundaries. [1](https://cdn.bazissoft.ru/documentation/ru/Cabinet.pdf)
- **Centering:** both vertical-panel placement and later panel moves provide a **“Центр”** action to place a panel in the center of a section. [1](https://cdn.bazissoft.ru/documentation/ru/Cabinet.pdf)
- **Symmetry:** Шкаф has a command to build a **mirror-symmetric cabinet** (“Построить зеркально симметричный шкаф”). [1](https://cdn.bazissoft.ru/documentation/ru/Cabinet.pdf)
- Мебельщик also has general-purpose symmetry tooling (“Разрешить симметрию … команда Симметрично отобразить”). [24](https://s3-cold.bazissoft.ru/documentation/ru/Bazis.pdf)

#### (d) How shelves/dividers are added/removed (split vs insert)

- Adding **vertical panels** and **horizontal panels** explicitly **splits a section into new sections** (“будут сформированы новые секции”). [1](https://cdn.bazissoft.ru/documentation/ru/Cabinet.pdf)
- Horizontal panels can be toggled as **removable shelves** via a **“Съемная”** option; the manual states constraints (e.g., after installing a removable shelf, horizontal panels can’t be installed in that same section). [1](https://cdn.bazissoft.ru/documentation/ru/Cabinet.pdf)
- Removal is explicit: “Удаление панелей” can delete vertical/horizontal panels, stiffness panels, and removable shelves; “Удалить элементы секции” clears all objects in a chosen section. [1](https://cdn.bazissoft.ru/documentation/ru/Cabinet.pdf)
- There is also a **conversion** operation: “Преобразование панелей в полки” converts stationary horizontal panels ↔ removable shelves, with constraints when the panel is a boundary for door-installed sections. [1](https://cdn.bazissoft.ru/documentation/ru/Cabinet.pdf)

#### (e) Base/upper/tall rows — structural relationship

- In the retrieved official documentation, **Шкаф** is primarily about **one cabinet/wardrobe composed of internal sections** rather than a kitchen-run concept (multi-cabinet ganging/equalize widths). [1](https://cdn.bazissoft.ru/documentation/ru/Cabinet.pdf)

#### (f) Terminology in UI/docs (RU/EN)

- RU terms explicitly used: **Структура модели**, **История**, **Эластичность**, **Секция**, **Вертикальные панели**, **Горизонтальные панели**, **Съемная (полка)**, **Удаление панелей**, **Построить зеркально симметричный шкаф**. [24](https://s3-cold.bazissoft.ru/documentation/ru/Bazis.pdf)
- EN UI terminology for Bazis isn’t present in the RU manuals I retrieved; Bazis also has an English product page for BAZIS‑Cabinet, but it doesn’t document the internal “section” editing operations at the level above. [26](https://bazissoft.com/design/cabinet)

### B) **imos iX (iX CAD / Article Designer workflow)**

#### (a) Core structural model (hierarchy)

- imos describes an **integrated data model** for iX CAD that stays consistent under changes/updates. [27](https://www.imos3d.com/en/products/design-order/ix-cad-1)
- In the **Article Designer** training material, cabinet structure is organized into **ADGs** (Article Designer Groups) and entries like **“Divider/Drawers”**, where you define a **Division** type (e.g., **Shelves**) and a **Part type** (e.g., **Adjustable shelf**). [2](https://soft-technik.net/download/B_05_Konstrukcja_szafy_z_frontem_imos_EN.pdf?srsltid=AfmBOopFg_KEwkZCIj5KnlNnibGNWJkcPN1vIumJn4AIpdJVX5iY_R7O)

#### (b) Dimension edit propagation (local vs group vs global; choosing scope)

- Article Designer supports **linear division strings** (e.g., fixed shelf “450mm:1:360mm”, adjustable shelf “1:1”, drawers “1:1:1”) that act like a parametric partitioning scheme. [2](https://soft-technik.net/download/B_05_Konstrukcja_szafy_z_frontem_imos_EN.pdf?srsltid=AfmBOopFg_KEwkZCIj5KnlNnibGNWJkcPN1vIumJn4AIpdJVX5iY_R7O)
- imos supports change tracking via a **Modifier stack**; modifications can be **saved permanently** using **“Global save”**, and the doc explicitly notes it can also be saved **order-related** (scope choice). [2](https://soft-technik.net/download/B_05_Konstrukcja_szafy_z_frontem_imos_EN.pdf?srsltid=AfmBOopFg_KEwkZCIj5KnlNnibGNWJkcPN1vIumJn4AIpdJVX5iY_R7O)
- iX CAD also supports a 2D-driven workflow where changing 2D drawing elements updates the 3D model (“By changing the 2D drawing elements, the 3D model can be adjusted…”). [27](https://www.imos3d.com/en/products/design-order/ix-cad-1)

#### (c) Alignment/symmetry/equal-spacing

- Equal spacing shows up primarily as **relative division patterns**: “1:1:1” is explicitly described as producing **three drawers of the same size**; the training material lists other relative/absolute patterns (e.g., “2:2:1”, “100mm:100mm:1”). [2](https://soft-technik.net/download/B_05_Konstrukcja_szafy_z_frontem_imos_EN.pdf?srsltid=AfmBOopFg_KEwkZCIj5KnlNnibGNWJkcPN1vIumJn4AIpdJVX5iY_R7O)

#### (d) Add/remove shelves/dividers (split vs insert)

- The training doc demonstrates “defining” fixed and adjustable shelves by selecting the relevant ADG entry and setting **Division: Shelves** with **Part type** choices (e.g., **Adjustable shelf**) and then entering a division expression—this is effectively an **insert-and-partition** model. [2](https://soft-technik.net/download/B_05_Konstrukcja_szafy_z_frontem_imos_EN.pdf?srsltid=AfmBOopFg_KEwkZCIj5KnlNnibGNWJkcPN1vIumJn4AIpdJVX5iY_R7O)
- Explicit “delete shelf” operations were not found in the retrieved imos training PDF (it focuses on construction + saving modifications). [2](https://soft-technik.net/download/B_05_Konstrukcja_szafy_z_frontem_imos_EN.pdf?srsltid=AfmBOopFg_KEwkZCIj5KnlNnibGNWJkcPN1vIumJn4AIpdJVX5iY_R7O)

#### (e) Rows (base/upper/tall) structural relationship

- iX CAD’s room-planning/production features include generating **long parts** such as **worktops, plinth/toe-kick strips, light/cornice strips** “on the basis of the room situation and the planned articles,” which is how multi-cabinet rows typically get coupled to shared parts. [21](https://www.imos3d.com/produkte/konstruktion-auftrag/ix-cad/)

#### (f) Terminology (RU/EN)

- EN terms explicitly used in sources: **Article Designer**, **Element Manager**, **Division**, **Shelves**, **Adjustable shelf**, **Modifier stack**, **Global save**. [2](https://soft-technik.net/download/B_05_Konstrukcja_szafy_z_frontem_imos_EN.pdf?srsltid=AfmBOopFg_KEwkZCIj5KnlNnibGNWJkcPN1vIumJn4AIpdJVX5iY_R7O)
- RU terminology in official UI/docs was not present in the sources I retrieved; RU terms may exist via localized reseller training, but I’m not citing that without a retrieved source.

### C) **Polyboard (Zones model, incl. “External Zones”)**

#### (a) Core structural model (hierarchy)

- Boole & Partners describes Polyboard as managing a **“structure de meuble arborescente”** (tree furniture structure) and rebuilding in real time based on: cabinet body dimensions + **internal separators (uprights/shelves)** + doors/drawers + manufacturing method rules. [16](https://boole.eu/fr/polyboard.php)
- A distributor manual (Spanish) explicitly documents the **“Concepto de Zonas y Multi‑Zonas”** and how to select them, treating the interior as a structured set of addressable volumes. [3](https://pdfcoffee.com/polyboard-iv-spanish-manual-pdf-free.html)
- Wood Designer (Polyboard training/reseller materials) documents **External Zones** as added volumes outside the main cabinet (top/bottom/back/sides) used for things like plinths, fillers, face frames, etc. [13](https://wooddesigner.org/face-frames-fillers-plinths-using-polyboard/)

#### (b) Dimension edit propagation (scope + choosing scope)

- Polyboard is presented as **parametric**: resizing updates the whole piece automatically (described as “redessine… et recalcule… au fur et à mesure de vos modifications”). [16](https://boole.eu/fr/polyboard.php)
- “Zone-scoped” behavior exists for at least manufacturing features: e.g., **regular drillings** can be defined **globally** or **“Zone by Zone”**, and shelves can be “locked to the nearest drillings” (individually or multizone). [28](https://boole.eu/pdf/PLB4_Recent_Features.pdf)
- A concrete propagation example: when hardware is locked into a 32mm drilling configuration, moving a shelf can cause hinge placement to adjust within constraints (as described in the Polyboard 32mm workflow article). [29](https://wooddesigner.org/using-the-32mm-system-with-polyboard-cabinet-software/)

#### (c) Alignment/symmetry/equal-spacing

- Equal division is documented strongly for drawers: “Polyboard inserts drawers that divide a volume into equal parts,” and you can later individualize divisions (by changing gap positions/distances). [12](https://wooddesigner.org/drawers-with-different-heights/)

#### (d) Add/remove shelves/dividers (split vs insert)

- The Spanish manual’s table of contents explicitly includes: **Añadir Estantes** (add shelves) and **Añadir Montante / División Vertical** (add uprights/vertical division), tied to the zones/multi-zones concept. [3](https://pdfcoffee.com/polyboard-iv-spanish-manual-pdf-free.html)
- External Zones can be used to create plinths/upper strips/fillers and can host additional structures (shelves/uprights) outside the main carcass volume. [13](https://wooddesigner.org/face-frames-fillers-plinths-using-polyboard/)
- Explicit “remove shelf/divider” UI steps were not present in the retrieved Polyboard sources (though multiple-selection deletion is mentioned as a feature). [28](https://boole.eu/pdf/PLB4_Recent_Features.pdf)

#### (e) Rows (base/upper/tall) structural relationship

- Polyboard supports multi-cabinet kitchen projects: adding/resizing cabinets, and **automatic snapping of cabinets into place** in a project layout. [22](https://wooddesigner.org/design-a-kitchen/)

#### (f) Terminology (RU/EN)

- EN/French vendor terminology: **structure arborescente**, **séparateurs internes (montants et étagères)**, “Zone by Zone,” “Inside Zone.” [16](https://boole.eu/fr/polyboard.php)
- Spanish distributor terminology: **Zonas**, **Multi‑Zonas**, **Estantes**, **Montante / División Vertical**, **Separadores “Nulos”** (zero-thickness separators). [3](https://pdfcoffee.com/polyboard-iv-spanish-manual-pdf-free.html)
- RU terminology wasn’t present in the retrieved Polyboard sources.

### D) **Cabinet Vision**

#### (a) Core structural model (hierarchy)

- Cabinet Vision “Solid” training materials describe an **Assembly** that you can **stretch** and then **section**; it uses a **Section Editor** that acts on **openings/sections** on the face and inside the case. [4](https://manualzz.com/doc/27236801/planit-version-5-cabinet-vision-solid-quick-start-guide)
- The same guide distinguishes **Face editing** vs **Case editing**, and notes “Face/Case logic transfer” (interior parts associated to face parts). [4](https://manualzz.com/doc/27236801/planit-version-5-cabinet-vision-solid-quick-start-guide)

#### (b) Dimension edit propagation (local vs linked to face sections; choosing scope)

- A user-forum discussion (Woodweb CAD forum) describes a concrete scope toggle: when adding interior fixed shelves/partitions, clicking the **dashed grey line** makes them **follow the face sections**, i.e., stay linked when door/opening sizes change. [30](https://www.woodweb.com/cgi-bin/forums/cad.pl?read=749154)
- A Hexagon case study states: “If I move a shelf, Cabinet Vision automatically moves the shelf studs… if I change a door size it moves all the associated fixtures and fittings.” [17](https://hexagon.com/resources/resource-library/cabinet-vision-costs-money-but-saves-lot-more)

#### (c) Alignment/symmetry/equal-spacing

# Parametric Component Libraries: A Cross-Tool Deep Dive

---

## 1. THE TOOLS AT A GLANCE

### 🟧 PolyBoard (Sub-Methods / Models)

**What it is:** A panel-based cabinet CAD/CAM tool built around a parametric motor and a layered library system called "Quick Design Libraries."

[5](https://wooddesigner.org/help-centre/polyboard-libraries/) PolyBoard uses the term "Quick Design libraries" to refer to both a group of libraries *and* to manufacturing methods and sub-methods. The libraries stock design components like materials, hardware, 3D accessories, and shapes — while the manufacturing methods act like style sheets, describing how those components should be used. [6](http://fittingsoftware.com.au/polyboard.htm) A very useful feature of PolyBoard is the ability to specify manufacturing methods — global rules that define how a cabinet is constructed, allowing easy cabinet creation by selecting a particular manufacturing method or just a particular sub-method. Sub-methods include a method for overall cabinet construction (joints, overlaps, recesses), as well as sub-methods for materials, edgebanding, hardware fittings, dividing panels, and the properties of drawers and doors.

---

### 🟦 Cabinet Vision (Object Catalog / UCS)

**What it is:** An enterprise-grade cabinetry design-to-manufacture platform (now by Hexagon) with a formal object catalog and programmable intelligence layer.

[11](https://learncabinetvision.com/projects) Cabinet Vision provides the ability to go well beyond its native capability by employing custom programming known as User Created Standards (UCS's), as well as the ability to embed object intelligence or shape intelligence into reusable library items. These powerful tools allow users to automate manual steps, provide decision logic for variable outcomes, remove or reduce engineering mistakes, and make complex objects or manufacturing processes easily repeatable.

**Mozaik** sits closer to the small-shop end: [16](https://sinclaircabinets.com/cabinet-design-software/)Mozaik's parametric design capabilities allow for custom catalog creation, meaning you can easily design and save specific cabinet styles, dimensions, and hardware configurations, accelerating future projects and ensuring consistency.

---

### 🟩 imos (Construction Principles / Article Designer)

**What it is:** A German-engineered furniture CAD/CAM platform built on AutoCAD with a deeply hierarchical "Element Manager" organizing Construction Principles (CPs), Part Definitions, and Articles.

[21](https://www.imos3d.com/en/products/design-order/ix-cad-1/) imos iX CAD has article libraries — a central administration of all library elements such as standard and special articles. The structure is freely definable and the contents can be easily built up and extended. In the article selection, individual furniture types including permissible design variants can be compiled in a catalog and configured via a convenient selection interface. [24](https://soft-technik.net/download/B_05_Konstrukcja_szafy_z_frontem_imos_EN.pdf) The construction of drawers and fittings are defined by a Construction Principle, which is imos's fundamental unit of reuse — a named, savable rule-set that governs how any part or sub-assembly is built, edged, machined, and connected.

---

### 🎨 Figma (Components & Published Libraries) — _UX Interaction Benchmark_

**What it is:** A cloud-native UI design tool whose component/library model is the gold standard for collaborative, live-updating parametric asset libraries.

[37](https://help.figma.com/hc/en-us/articles/360041051154-Guide-to-libraries-in-Figma) In Figma, a library is a collection of design assets like components, styles, and variables. These design assets live in a single file, but can be reused across different files or projects. People often use libraries for sharing common design elements like buttons, icons, pieces of UI, colors, or values for certain properties — helping everyone stay consistent and making it easy to build from existing designs.

---

### 🏗️ SketchUp (Dynamic Components / Live Components) — _UX Interaction Benchmark_

**What it is:** A 3D modelling tool with a formula-driven "Dynamic Component" system and an emerging "Live Components" successor.

[41](https://extensions.sketchup.com/en/content/dynamic-components) Dynamic Components are components with special attributes that allow for more advanced functionality. In some cases, a dynamic component may include parametric functions — a stair, for example, that when resized, automatically adds more steps. [41](https://extensions.sketchup.com/en/content/dynamic-components) In other cases, a dynamic component may include clickable interactions — for example, a cabinet whose doors can open and close when a user clicks with SketchUp's Interact Tool. And in other cases, a component may be dynamic because it includes additional information attributes, such as a faucet with a Product ID, material finish, and so on.

**PolyBoard — model saving:**

[1](https://wooddesigner.org/help-centre/polyboard-set-up-and-overview/) You can design very quickly in PolyBoard, but to work even faster it is recommended to build up a library of models over time. It is then easy to open them up for future jobs and modify as required. [3](https://wooddesigner.org/polyboard-software-tools/) Add to your project as you design or create a model library and simply resize to fit your next project. [3](https://wooddesigner.org/polyboard-software-tools/) You can build your own model catalogue for internal use or open it up to customers as an ordering portal.

**Cabinet Vision — catalog save:**

[17](https://planitcanada.ca/blog/awesome-resources/modify-cabinets-expand-design-catalog-cabinet-vision/) Cabinet Vision empowers users to streamline their design-for-manufacturing operations efficiently. If you find yourself repeatedly performing similar tasks or adjustments for different projects, the solution is simple: make the adjustment once, save the cabinet to the catalog, and easily retrieve it for future projects. This intelligent approach minimizes redundancy and enhances workflow efficiency. [17](https://planitcanada.ca/blog/awesome-resources/modify-cabinets-expand-design-catalog-cabinet-vision/) Cabinets in Cabinet Vision are not static. The object catalog on the left-hand side is essentially a list of cabinet designs saved to the catalog, to the library, so that you don't have to redraw them every single time you open a new job. You can sort and arrange them however you like, and every time you grab an object, you can bring it onto the wall without redrawing that same design.

**imos — Article Designer global save:**

[24](https://soft-technik.net/download/B_05_Konstrukcja_szafy_z_frontem_imos_EN.pdf) To save changes permanently, click on the "Global save" button in the Article Designer. [24](https://soft-technik.net/download/B_05_Konstrukcja_szafy_z_frontem_imos_EN.pdf) Create a CP together with the necessary Part Definitions and save it in your personal folder.

**Figma — component creation:**

[38](https://wpdean.com/how-to-use-components-in-figma/) Select any frame, group, or layer you want to reuse, then convert it to a main component using the right-click menu or keyboard shortcut. The element displays a purple diamond icon in the Layers panel after conversion. [38](https://wpdean.com/how-to-use-components-in-figma/) Main components act as the single source of truth for your design system in Figma.

[42](https://help.sketchup.com/en/sketchup/making-dynamic-component) Save the component in a separate file that you can import into other models from the Components browser or share with others within 3D Warehouse. For the component to work, make sure you context-click the highest level of the component and select Save As from the menu that appears.

### (b) Parametrization — What Stretches/Scales vs. Stays Fixed

This is the most critical dimension for a mobile "premade section" app. Each tool draws the line differently:

#### PolyBoard: Dimension-driven re-proportioning with fixed construction rules

[1](https://wooddesigner.org/help-centre/polyboard-set-up-and-overview/) Because PolyBoard is parametric, you can adjust the overall dimensions and all parts automatically resize. The key insight is *what* the parametric motor holds constant: material thickness, joint overlaps, hardware positioning rules, and edgebanding logic are fixed in sub-methods. Only the outer envelope dimensions (H × W × D) drive the re-scaling. [6](http://fittingsoftware.com.au/polyboard.htm) Inner shapes are applied parametrically so that when the cabinet is resized, routing is maintained in the same position on the part. This means hardware holes, grooves, and cut-outs are position-locked (e.g., "32mm from edge") rather than proportionally scaled. [3](https://wooddesigner.org/polyboard-software-tools/) Resize your project or change components, and all hardware is dynamically moved, added or removed as required.

**Rule:** Outer box → scales. Thickness, joint offsets, hardware spacing → fixed absolute values.

#### Cabinet Vision: Constraint-based xShaping + formula-driven attributes

[18](https://www.ligna.de/apollo/ligna_2025/obs/Binary/A1423352/EMEA_UK_2020_MPS_CABINET_VISION_Brochure_EN_RLL4_391.pdf) xShaping provides the capability to parametrically shape assemblies, parts, and routes utilising both simple and advanced constraints. [15](https://slashdot.org/software/p/CABINET-VISION/) The software's intuitive parametric functionality allows users to easily adjust previous custom designs, resizing components without the need for extensive reprogramming.

Users can define size lists and conditional logic via UCS so that, for example, a door switches from single to double when width exceeds 600mm. What stays fixed: construction style (face-frame vs. frameless), hinge boring patterns, default toe-kick height — all encoded in the catalog item itself.

#### imos: Construction Principles as fixed contracts, Article Designer as variable envelope

[21](https://www.imos3d.com/en/products/design-order/ix-cad-1/) The Designer article is ideal for variable-size constructions. This module covers requirements in cabinet and object construction when similar furniture with different dimensions or front divisions is required. The Article Designer accesses parametric components. [25](https://support.imos3d.com/fileadmin/imosOnlineHelp/iX2017/ENG/Content/Resources/Topics/Whats_New/WhatsNew_CAD_EM.htm) If Article is selected as the construction principle, it is possible to define different sub-articles depending on the height of the article.

In practice, a Construction Principle defines: which edges get banded (fixed edging code like `1001`), what machining operations run, and how connectors are placed. The overall article H/W/D are free variables. imos also supports "data ranges" that limit which dimension values are valid.

[23](https://soft-technik.net/download/B_14_Zasady_szuflad_EN.pdf) You can define a fixed dimension or several valid values. The program compares the dimension of the insertion zone and considers the distances to the shelves and the frame.

#### SketchUp Dynamic Components: Formula-based attributes, scale-tool tension

[50](https://how-to-sketchup.com/how-to-create-dynamic-components-in-sketchup/) Dynamic components can change size, position, and appearance based on user inputs or programmed parameters.

The parametric formula system lets you write rules like `LenX = Width` and `Copies = INT(LenX / 100)` so that, for example, fence pickets replicate as the component is stretched. However, there is a known tension: [44](https://forums.sketchup.com/t/dynamic-component-scale-and-parametric/146247)if you make a component parametrically size-editable, user input via the scale tool (along the same axis) just gets ignored. A solution would be a size change by scaling feeding and updating the user-editable option panel and vice versa.

The newer Live Components resolve this: [45](https://mastersketchup.com/live-components/)Live components are parametric, allowing you to configure the component using various predetermined parameters while seeing the results in real-time. Once configured, you can download and import it into SketchUp.

#### Figma: Layout-constraint autolayout, not physical dimensioning

Figma's parametrization is spatial/layout, not physical. Components use Auto Layout (flexbox-like) so padding, gap, and alignment are fixed constraints while content drives size. Variants let a single component swap between discrete states (size: S/M/L, state: default/hover/active).

[38](https://wpdean.com/how-to-use-components-in-figma/) Variants combine related components into a single component set with switchable properties like size, state, or style. Select two or more similar components, right-click > Combine as variants, or click "Combine as variants" in the Design panel. Configure variant properties in the right sidebar: name each property (Size, State, Type) and define values (Small/Medium/Large, Default/Hover/Active).

**Summary Table — What Scales vs. Stays Fixed:**

|Tool|Scales with resize|Stays fixed|
|---|---|---|
|**PolyBoard**|Outer H/W/D; shelf count (auto-added)|Material thickness; joint overlaps; hardware hole offsets (absolute mm)|
|**Cabinet Vision**|Carcass envelope; conditional part logic (UCS)|Construction style; boring patterns; toe-kick height|
|**imos**|Article H/W/D; insertion zone logic|Edging codes; machining operations; connector types (from CP)|
|**SketchUp DC**|LenX/Y/Z formulas; child counts|Fixed sub-component attributes; scale tool conflict with parametric input|
|**Figma**|Frame width/height driven by content + Auto Layout|Padding; gap; corner radius; typography; defined variant states|

### (c) Instance Overrides vs. Master Edits

This dimension defines the most important UX decision: _when does a local change affect only this instance vs. propagating to all?_

#### PolyBoard: Instance-level edits, no master propagation

[1](https://wooddesigner.org/help-centre/polyboard-set-up-and-overview/) To make changes to an individual unit inside a project, double-click on it inside the edit window. The model will open inside Cabinet mode where you make your changes. Close and save, and those changes will be reflected in Project mode.

PolyBoard's model files are independent — there is no live master-to-instance link. When you open a model from the library and resize it, you are making a copy. Changes to the saved model file do not retroactively update instances already placed in a project. This is analogous to a _detached_ component model.

[5](https://wooddesigner.org/help-centre/polyboard-libraries/) It is always possible to directly edit and change the material of a part, or add a hinge to a specific door. But [5](https://wooddesigner.org/help-centre/polyboard-libraries/) for efficient production it's much better to build your preferences into a manufacturing method so you can apply them with the click of a button. Sub-methods serve as the closest thing to a "master" — updating a sub-method applies it forward to new cabinets but does not retroactively change already-placed ones.

#### Cabinet Vision: Catalog item as master; instance-level modifications are project-local

[17](https://planitcanada.ca/blog/awesome-resources/modify-cabinets-expand-design-catalog-cabinet-vision/) Any cabinet or object taken from the catalog can be modified to be any other design. However, like PolyBoard, modifications made within a project do not push back to the catalog master. The catalog is a template; the instance is a local derivative. [17](https://planitcanada.ca/blog/awesome-resources/modify-cabinets-expand-design-catalog-cabinet-vision/) Users can adjust construction methods, colours, materials, and hardware settings tailored to individual cabinets while ensuring dynamic changes that respond intelligently to modifications.

Cabinet Vision's UCS layer adds a form of master-level logic: a UCS governs _all_ instances of an object type. Editing a UCS propagates new behaviour to all objects of that type when re-inserted or re-generated.

#### imos: Global Save → master update; Modifier → instance override

imos has an explicit two-path system:

- **"Global save"** in the Article Designer commits changes back to the master Article/CP in the database — affecting all future insertions and, in some workflows, already-placed items upon regen.
- **"Modifier"** applies a local override to a specific instance. [24](https://soft-technik.net/download/B_05_Konstrukcja_szafy_z_frontem_imos_EN.pdf)In previous steps, the pull height was changed by a "Modifier." However, the pull height can also be changed via data setup — and the following steps show how to change the pull height by changing your data (i.e., the master CP), illustrating the explicit two-path choice.

[29](https://www.getapp.com/construction-software/a/imos-ix/) imos iX allows team members to automatically re-generate design, furniture, and assembly 3D models based on updates across detail and production drawings. This is the closest to Figma's live update model in the furniture CAD space.

#### Figma: The gold standard — live master-instance link with selective override preservation

[32](https://help.figma.com/hc/en-us/articles/360039150733-Apply-changes-to-instances) The main component defines the properties of the element; the instance is a copy of the component you can reuse in your designs. You can make changes to any instance of a component you add to your file. These changes allow you to customize an instance to suit its new context, or explore iterations of a design. [33](https://help.figma.com/hc/en-us/articles/360038665934-Edit-main-components) Any instance you create is linked to the main component. When you make changes to the main component, Figma will apply any changes to any linked instances. If you are using instances within the same file as your main components, Figma applies changes immediately. If the components are published to a library, you need to publish those changes to see updates in subscribed files.

Override preservation is nuanced: [39](https://wpdean.com/how-to-edit-a-component-in-figma/)instances with overrides retain their local changes while inheriting non-conflicting updates.

"Push to main" allows the reverse flow: [33](https://help.figma.com/hc/en-us/articles/360038665934-Edit-main-components)there may be situations where you want changes applied to an instance to apply to the main component as well. You can use the "Push overrides to main component" setting to apply any overrides to the main component, which will also update any other instances of that component. However, [33](https://help.figma.com/hc/en-us/articles/360038665934-Edit-main-components)you can only push overrides if the main component is in the same file as the instance — it's not possible to push overrides to components in another file, including published libraries.

#### SketchUp: Definition → all instances; explicit detach for independence

[48](http://help.sketchup.com/en/sketchup/developing-components-and-dynamic-components) Every component has a definition and an instance. A definition outlines how all components of a specific type appear and behave in the drawing area. When you insert a component into a model, you create a component instance based on its definition.

By default, editing a component in SketchUp updates all instances sharing that definition. To make an instance independent, you must explicitly "Make Unique" — after which it gets its own definition.

## 4. RECOMMENDED MENTAL MODEL FOR MOBILE: "PREMADE SECTIONS + USER-BUILT LIBRARY"

Based on the cross-tool analysis, here is a proposed mental model that borrows the best patterns from each system and makes them explicit for a mobile parametric design context.

---

### 🏛️ Mental Model: The "Section Template → Instance → Override" Stack

Think of the system as **three layers**, each with explicit parametrization rules:

text

```
┌─────────────────────────────────────┐
│  LAYER 3: SECTION TEMPLATE (Master) │  ← Premade by app / shared library
│  What lives here: structural rules  │
│  H/W/D ranges, sub-part formulas,   │
│  hardware CPs, material slots        │
└─────────────┬───────────────────────┘
              │ "Use Template"
              ▼
┌─────────────────────────────────────┐
│  LAYER 2: CONFIGURED ASSEMBLY       │  ← User fills in dimensions + options
│  What lives here: user choices       │
│  Specific H/W/D, door type,          │
│  material selections, hardware SKU   │
└─────────────┬───────────────────────┘
              │ "Save to My Library"
              ▼
┌─────────────────────────────────────┐
│  LAYER 1: USER LIBRARY ITEM         │  ← User's reusable component
│  What lives here: frozen config +   │
│  parametric flexibility envelope     │
│  (can resize within valid ranges)    │
└─────────────────────────────────────┘
```

---

### 📐 Explicit Parametrization Rules for Mobile

These rules should be surfaced explicitly in the UI, not buried in docs:

**Rule 1 — The Envelope Rule** _(inspired by PolyBoard + imos)_

> The outer dimensions (H, W, D) are always free variables within a defined valid range. Every other property is either _fixed by the template_ (material thickness, joint type, hardware offsets) or _user-selectable from a list_ (material, door style, colour).

On mobile: a **range slider** for H/W/D with min/max stops set by the template. A lock icon indicates template-fixed properties.

**Rule 2 — The Absolute Offset Rule** _(inspired by PolyBoard sub-methods)_

> Hardware positioning (hinge centres, shelf pin spacing, drawer runner height) is stored in **absolute millimetre offsets from reference edges** — not as proportional percentages. When the cabinet is resized, offsets stay fixed; only the cavity between them changes.

On mobile: show this as "32mm from top" labels on a diagram — not percentages.

**Rule 3 — The Conditional Count Rule** _(inspired by SketchUp Dynamic Components + Cabinet Vision UCS)_

> Sub-components that repeat (shelves, drawer stacks, door leaves) use a **count formula** tied to the envelope dimension. Example: `shelf_count = FLOOR((H - 150) / 250)`. Users can override the formula count up or down within template limits.

On mobile: a stepper (+/−) control per repeating element, with the auto-calculated value pre-filled.

**Rule 4 — The Instance Override Rule** _(inspired by Figma)_

> Any property can be overridden on a specific placed instance _without_ breaking the link to the template. However, overrides that conflict with structural template rules (e.g., thickness) are blocked with an explanation.

On mobile: a **"customized" badge** on overridden instances. A "reset to template" one-tap restore.

**Rule 5 — The Master Propagation Rule** _(inspired by Figma + imos regen)_

> When the user edits a template that is live-linked, all instances in the current project receive a **"update available" notification** and can accept or reject the update. Accepted updates merge with existing overrides using the layer-ID approach (non-conflicting overrides preserved).

On mobile: an **orange dot** on affected instances with a single-tap "Update all" or per-instance "Review" option.

**Rule 6 — The Save-Back Rule** _(inspired by Figma's "Push to main")_

> If a user has customized an instance and wants to promote it to a personal library template, they tap "Save as new template." The override set becomes the new master. Changes do _not_ retroactively push to the existing library item (to avoid destroying peers' work).

On mobile: a **"Save to My Library"** action accessible from the instance context menu, with a name + category field.

---

### 🗂️ Library Organization on Mobile

Adopt Figma's **slash-path naming convention** mapped to a mobile-friendly category tree:

text

```
Cabinets / Base / Single Door
Cabinets / Base / Two Drawer
Cabinets / Wall / Open Shelf
Sections / Corner / L-Shape
Hardware / Blum Hinge / 110°
Materials / White Melamine 18mm
```

- **Search** is full-text across name, tags, and material type (borrowing from 3D Warehouse + Figma Assets Panel)
- **Filters**: by room, by width range, by material, by "My Library" vs. "Premade"
- **Recents** and **Favourites** rails at the top of the library panel (analogous to PolyBoard's Quick Design shortcuts)

---

### 🔄 Sharing Model for Mobile

|Tier|Mechanism|Inspired by|
|---|---|---|
|**Personal**|Local device library; exportable as `.json` or `.zip` package|PolyBoard folder export|
|**Team**|Cloud-synced shared workspace; explicit publish step|Figma Team Library|
|**Marketplace**|In-app store of curated template packs (premade sections)|3D Warehouse + Figma Community|
|**Interop**|Export to CSV (for cut-list), DXF (for CNC), or PDF (for client)|imos XML + Cabinet Vision CSV|

The key sharing insight from Figma that should be mandatory: **a version history on each template**, so teams can roll back and consumers of the template can see a changelog before accepting updates.

---

### ⚠️ The Four Pitfalls to Avoid (Learned from the Tool Survey)

1. **PolyBoard pitfall — no live link:** Don't build a library where saving a new version of a template silently leaves old instances stale. Always surface a "template updated — instances may be out of date" warning.
    
2. **SketchUp DC pitfall — scale-tool conflict:** Don't allow two competing resize pathways (drag-to-scale AND numeric input) that can fight each other. Pick one canonical input method per axis and disable the other. SketchUp's Live Components are the right lesson here.
    
3. **imos pitfall — expert-only save:** Don't bury the "promote to master" action inside a deeply nested dialog. Surface it as a first-class action whenever a user finishes configuring an instance they're proud of.
    
4. **Figma override pitfall — layer-ID fragility:** [34](https://forum.figma.com/ask-the-community-7/publishing-updating-components-overrides-existing-text-16925)Each layer has its own unique ID. By deleting a layer and adding a new one, the layer IDs will no longer match between the library objects and the design file objects, which is why overrides are reset. In a furniture context, this means: never change the _name_ of a parametric sub-part in a template without a migration step — doing so will break all existing instance overrides referencing that part by ID.

This mental model — **Section Template → Configured Assembly → User Library Item**, with the six explicit parametrization rules, mobile-first library organization, and a tiered sharing model — gives users the speed of premade sections and the power of a fully personalized, properly parametric component library.

## TL;DR (the pattern you can steal)

Across cabinet/millwork “parametric CAD/CAM” tools, a _user-built library item_ is almost never “just geometry.” It’s usually:

1. a **parametric recipe** (what parts exist + how they’re related), plus
2. a referenced **standards bundle** (materials, joinery, hardware placement rules, schedules), plus
3. **metadata** (thumbnail, categories, allowed options/variants), plus
4. a **distribution wrapper** (folder/package/catalog that can be copied, locked, versioned, or sold).

Figma and SketchUp are the clean interaction benchmarks: **Main component ↔ instances, with overrides**; and **Dynamic component attributes + user-configurable options**. [1](https://help.figma.com/hc/en-us/articles/360038665934-Edit-main-components)

---

# A shared vocabulary (so the comparisons line up)

- **Master / Definition**: the source template (“main component” in Figma; “component definition” in SketchUp; a saved cabinet/article/product in cabinet software).
- **Instance**: a placed copy in a project/job/room. Often resizable/configurable.
- **Standards / Methods**: rulesets that decide _construction_, not just size (panel thickness, reveals, hardware rules, drilling patterns, joinery).
- **Overrides**: instance-specific changes that don’t (yet) alter the master.
- **Publish / Distribute**: making the library usable by others (team library, read-only catalog, marketplace listing, file/folder copy).

---

# 1) PolyBoard (Models + Manufacturing Methods/Sub-methods)

PolyBoard is explicit about splitting “what the cabinet is” (a **model**) from “how you build it” (a **manufacturing method**, made of **sub-methods**—style sheets for carcass, materials, edge banding, hardware rules, drawers/doors, drillings, etc.). [2](https://wooddesigner.org/help-centre/polyboard-manufacturing-methods/)

## (a) Save a configured assembly as a reusable component

**What you save** is effectively a _cabinet model file_ that you can keep in your **model library** and reuse:

- Their “Catalogue mode” is explicitly for producing manufacturing docs from models you already have “in your own library,” and for batch production/pricing. [3](https://wooddesigner.org/help-centre/polyboard-catalogue-mode-overview/)
- In Project mode you can “Add” existing cabinet files and drag them from the “Model list” into a room/project. [4](https://wooddesigner.org/help-centre/polyboard-multi-cabinet-projects/)

So the “Save as component” mental move is: **Save cabinet model → it becomes a library model you can drag/insert later**.

## (b) Parametrization: what stretches/scales vs stays fixed

PolyBoard markets the core behavior clearly:

- You “resize the carcass and all components resize.” [5](https://wooddesigner.org/design-a-kitchen/) But “what stays fixed” is largely controlled indirectly via **sub-method rules**, not by ad‑hoc per-instance scaling:
- Manufacturing methods are groups of sub-method “style sheets” that define construction preferences, and you can build/copy/edit them. [2](https://wooddesigner.org/help-centre/polyboard-manufacturing-methods/)
- Sub-methods include _Divisions_ (e.g., treat mobile shelves differently from fixed shelves) and _Regular drillings_ (hole rows) and more. [2](https://wooddesigner.org/help-centre/polyboard-manufacturing-methods/)
- In the 32mm-system workflow, resizing or moving shelves can add/remove holes automatically and adjust hinge positioning to fit rules. [6](https://wooddesigner.org/using-the-32mm-system-with-polyboard-cabinet-software/)

**Practical takeaway:** PolyBoard’s “don’t stretch the knob into an oval” equivalent is achieved by **rule-based regeneration** (hardware placement rules, drilling rules), not by geometric scaling.

## (c) Instance overrides vs master edits

Project mode gives you a clean “component instance” analog:

- If you drag in the _same_ cabinet design multiple times and edit it, “all instances of the cabinet will be updated.”

# Recommended mobile mental model: “Premade sections + everyone builds their own library”

Below is a _mobile-first_ mental model that maps cleanly onto the behaviors users already learned from Figma/SketchUp, while matching cabinet-software realities (standards bundles, hardware rules, etc.).

## 1) The objects users see (keep it to 3 nouns)

### A. **Section Template** (the “master”)

A Section Template is a **parametric recipe** + **default standards reference**.

- Think: **Figma main component** [1](https://help.figma.com/hc/en-us/articles/360038665934-Edit-main-components)
- Also think: **Cabinet Vision catalog item / Mozaik library product / PolyBoard model** [10](https://planitcanada.ca/blog/awesome-resources/modify-cabinets-expand-design-catalog-cabinet-vision/)

### B. **Section Instance** (placed in a project)

An instance is what’s actually in the room/job. Instances can carry **overrides**.

- Think: **Figma instance with overrides** [39](https://www.figma.com/blog/components-in-figma/)

### C. **Construction Standard** (the “method”)

This is the shop-wide “how we build” layer (materials, thicknesses, reveals, joinery, drilling system, hardware placement rules).

- Think: **PolyBoard manufacturing methods/sub-methods** [2](https://wooddesigner.org/help-centre/polyboard-manufacturing-methods/)
- Think: **Mozaik construction parameters / standard construction methods** [17](https://sites.google.com/view/mozaikonlinehelp/help/libraries/products-library/construction-parameters)
- Think: **imos construction rules/principles** [24](https://soft-technik.net/download/B_06_Zasady_Konstrukcyjne__imos_EN.pdf?srsltid=AfmBOooUOcQrPkqQI57P7b5hBaAKgVPG8YMYAj6e7--xBaWxwASIIWD2)

On mobile: always show users which Standard a section is using, because it explains “why it behaves that way.”

## 2) Make parametrization rules explicit (the “stretch map”)

Most user frustration comes from not knowing _what changes when size changes_. So define (and surface) 4 resizing behaviors, and apply them consistently.

### Behavior types (borrowed from Figma + SketchUp DC)

1. **Fixed** — never changes size
    
    - Examples: material thickness, hardware geometry, handle size.
    - Analog: SketchUp constrained subcomponents; Figma “Fixed width/height.” [35](https://help.sketchup.com/en/sketchup/constraining-attributes-dynamic-component)
2. **Stretch** — absorbs leftover delta continuously
    
    - Examples: a single open bay that just gets wider; a panel that can legitimately get taller.
    - Analog: SketchUp unconstrained LenX/LenZ; Figma “Fill container.” [35](https://help.sketchup.com/en/sketchup/constraining-attributes-dynamic-component)
3. **Repeat** — adds/removes copies rather than scaling one part
    
    - Examples: adjustable shelf pin holes on a system; slats/pickets; drawer stack count.
    - Analog: SketchUp “Copies” attribute patterns; PolyBoard/imos rule-based regeneration rather than scaling. [34](https://help.sketchup.com/ko-kr/sketchup/dynamic-component-predefined-attributes)
4. **Lock** — stays constant _within a layout_, and other parts stretch instead
    
    - Example: Mozaik explicitly supports locking opening height/width so resizing the cabinet doesn’t change that opening. [16](https://mozaik.support.cyncly.com/hc/en-us/articles/44831885477905-Mozaik-Product-Editor-Customer-Guide)
    - Mobile UI: each “opening” gets a Lock toggle.

### The resizing algorithm (make it predictable)

When a user changes overall **W/H/D**:

1. Apply **Fixed** dimensions first (thickness, toe-kick height if fixed, hardware clearances).
2. Preserve all **Locked** opening dimensions. [16](https://mozaik.support.cyncly.com/hc/en-us/articles/44831885477905-Mozaik-Product-Editor-Customer-Guide)
3. Distribute remaining delta to **Stretch** regions (proportionally or by weight).
4. If delta crosses thresholds, update **Repeat** regions (add/remove shelves/holes/modules) and then re-run steps 1–3.

This matches how cabinet tools behave in practice (rules regenerate outputs; holes appear/disappear; hardware repositions) and avoids the “scaled knob” problem by design. [6](https://wooddesigner.org/using-the-32mm-system-with-polyboard-cabinet-software/)

## ATTACK 1 — THE MOST DANGEROUS CLAIM IN THE ENTIRE DOCUMENT

### Target: "Rule 5 — The Master Propagation Rule / orange dot / live-link / override preservation"

**Verdict: Fatally underspecified, empirically unreliable, and will corrupt user data in production.**

This is the single most seductive claim in the original and the one most likely to cause a production catastrophe. The original borrowed Figma's "live master-instance link with selective override preservation" and proposed applying it directly to a mobile furniture parametrics context. Here is why that is wrong in Figma itself, let alone in a mobile CAD app.

**Failure evidence — Figma's own forums, multiple threads:**

[1](https://forum.figma.com/ask-the-community-7/component-overrides-get-broken-after-library-publish-27231) When a new library update is published, taking updates in the design file breaks overrides. The component variant selection is intact and even the override values are intact — however, instances either lose border radius, or have their alignment changed, or the layer name resets to the original from the atomic component. This happens to specific components and not others — and also randomly, sometimes some components break while others don't.

This is not a corner case. [1](https://forum.figma.com/ask-the-community-7/component-overrides-get-broken-after-library-publish-27231)It is described as "very current and a huge problem." Almost every instance of large component sets such as buttons and images are overridden when published to the library after a small change such as spacing. Users report that it "renders the product largely useless as a DS platform. All efficiency is gone."

The root mechanism causing this is not a bug that will be patched — it is structural. [8](https://forum.figma.com/ask-the-community-7/publishing-updating-components-overrides-existing-text-16925)Each layer has its own unique ID. By deleting a layer and adding a new one, the layer IDs will no longer match between the library objects and the design file objects, which is why overrides are reset.

The original document mentioned this as a footnote — "Pitfall #4" — while simultaneously recommending live-link propagation as "Rule 5." That is self-contradictory. You cannot recommend the feature that relies on ID stability as a first-class UX affordance while burying the fact that ID stability routinely breaks in the same document's footnotes.

**The furniture-specific amplification of this failure:**

In Figma, the user loses a text override on a button. They retype it in 3 seconds. In a furniture CAD app, the user has configured a kitchen run of 14 cabinets — each with specific material overrides, hardware selections, and dimension tunings — and a template update from the shared library wipes all of them simultaneously. The user is on a low-end Android device, possibly offline at the time, and has no immediate recourse. This is not a UX annoyance. This is data loss in a construction document.

The original's naming convention warning — "never change the name of a sub-part without a migration step" — is operationally useless advice for user-generated libraries on mobile. You cannot enforce naming discipline across hundreds of users who are, by the app's own design premise, non-expert builders.

**What the original missed entirely:**

[2](https://medium.com/@alexhris/pro-tip-updating-a-components-structure-in-figma-without-introducing-breaking-changes-fb89ba0d7b38) Even in straightforward cases like updating a button used throughout dozens or hundreds of screens, the fix is non-trivial — and one practitioner states: "I still consider that this is an issue Figma can easily fix." That was written in 2025. It is still open. [10](https://forum.figma.com/ask-the-community-7/what-can-you-change-in-a-library-component-before-it-breaks-instances-28428) A renaming of a boolean property — from "Checkbox" to "Row Selector" — is enough to break all instances. The boolean name change caused all instances with checkboxes turned on to turn off, because the name association was broken.

In a furniture library, the equivalent is: renaming a part from `"door_panel"` to `"door_leaf"` for better taxonomy silently detaches every instance override of that part across every user's project that has ever used the template.

**The Figma override preservation rule**, as documented officially, is:

[7](https://help.figma.com/hc/en-us/articles/360039150733-Apply-changes-to-instances) Position of any layers within the component cannot be overridden at instance level — you must detach or make changes to the main component. Figma uses layer names to determine whether to preserve a change on an instance: the layer names of the current instance and the variant or instance you're selecting must match — this applies both when swapping instances and selecting variants.

So the mechanism is name-matching, not ID-matching. The forums contradict this by showing name-identical layers still breaking. The conclusion is that the system is not reliably specified even by its creators.

**Bottom line on Attack 1:** The live-link propagation model is **not ready to be borrowed as a "gold standard" for a mobile furniture app**. The original dressed up a known-broken Figma behaviour as the recommended UX pattern. Do not ship Rule 5 as designed.

## ATTACK 2 — "FIGMA AS INTERACTION BENCHMARK" IS CATEGORICALLY WRONG FOR THIS DOMAIN

**Verdict: Wrong comparison class. Survives as inspiration only, not as architecture.**

Figma is a 2D vector layout tool. Its parametric system is spatial: Auto Layout is flexbox. Its components have no physics, no dimensional constraints beyond spatial containment, no material property inheritance, no unit system, and no concept of a valid-dimension range. The original conflates "visually similar interaction patterns" with "transferable architecture."

The specific failure this creates:

In Figma, a component at 400px wide and 400px tall is equally valid. In a furniture parametric system, a wall cabinet 200mm wide and 2400mm tall is **physically impossible** — it falls over. The parametric engine must encode validity ranges (min/max H/W/D ratios, thickness-to-span structural limits) as first-class constraints. Figma has no analogue for this. None of the six rules in the original model encodes validity constraints. There is no mention of a rule that says: "when the user resizes a shelf span beyond 900mm without a centre support, the system must block or warn." This is not a UX nicety. In a downstream CNC-to-production pipeline, a structurally invalid assembly becomes a cut list, gets machined, and fails in the customer's home.

**What survives from the Figma comparison:**

- The slash-path naming convention for library organization: ✅ Survives. It is a portable pattern independent of parametric architecture.
- The publish/subscribe library sharing model: ✅ Survives as _concept_, not as implementation. The actual Figma implementation of override propagation does not survive (see Attack 1).
- The "Assets Panel full-text search": ✅ Survives as a UX target.
- The "live master-instance link": ❌ Does not survive. See Attack 1.
- "Push to main": ❌ Does not survive at cross-file scope. [7](https://help.figma.com/hc/en-us/articles/360039150733-Apply-changes-to-instances)It is not possible to push changes to components in another file, including published libraries. It is also not possible to push changes to a component nested within another component. This directly breaks the "Save-Back Rule" (Rule 6) as proposed.

## ATTACK 3 — SKETCHUP DYNAMIC COMPONENTS ARE PRESENTED AS A CAUTIONARY TALE BUT THE SCALE-TOOL BUG IS WORSE THAN DESCRIBED

**Verdict: The original correctly identified the conflict but underestimated its severity and scope.**

The original said: "If you make a component parametrically size-editable, user input via the scale tool just gets ignored." That is the benign version of the bug.

The actual production failure is more severe: [13](https://3dshouse.com/sketchup/fix-dynamic-components-scale-sketchup-tool/)The cause of scale errors when copying a Dynamic Component is that child objects still mistakenly recognize the parameters of the original parent object. Especially if Groups are located inside a Dynamic Component, this error is almost certain to happen. This is described as a default bug of the SketchUp software.

And the formula-ID corruption on copy is a separate failure: [16](https://forums.sketchup.com/t/dynamic-component-scaling/183679)Dynamic components occasionally lose the ability to Scale properly. Instead of populating sub-components when using the Scale tool, the whole assembly scales as if it was a regular component. For example, a component designed to add more panels when scaled will instead stretch everything.

This means: a user copies a parametric cabinet component from the library, pastes it into a new position, resizes it — and silently gets a stretched monolith instead of a properly parametric assembly. This is not an edge case. It is triggered by the most basic user action: copy-paste-resize.

**What this means for the proposed mobile mental model:** Any mobile parametric system that uses copy-paste-resize as the core workflow (which the "premade sections" premise implies) must have explicit formula-rebinding on copy, not inherited parent-formula references. This is an implementation constraint the original did not surface.

**What survives from the SketchUp analysis:** The explicit recommendation to avoid competing resize pathways (Rule 2 of the proposal) survives and is now better justified: the SketchUp forum evidence proves this is not a theoretical concern but a documented production failure spanning at least 2016–2026.

## ATTACK 4 — THE "CONDITIONAL COUNT RULE" (RULE 3) IS DEMO CODE, NOT PRODUCTION CODE

**Target: `shelf_count = FLOOR((H - 150) / 250)` presented as a parametrization rule.**

**Verdict: Correct in principle, catastrophically incomplete in specification.**

The formula is trivially correct for a single-shelf-pitch cabinet. Here is what the original did not address:

1. **The formula produces integer outputs that create discontinuous jumps.** At H=549mm, `shelf_count=1`. At H=550mm, `shelf_count=2`. This means a 1mm resize triggers a complete structural reconfiguration — a new part appears, new edgebanding runs, new connectors are specified, and the cut list changes. In a CNC-to-production pipeline, this is not a UI event — it is a new machining job. The user has no visibility into this unless the app explicitly surfaces "this resize will change your part count and cut list."
    
2. **The formula assumes uniform shelf pitch.** Real kitchens have: adjustable shelves (32mm grid spacing), fixed shelves (mid-support for spans >900mm), pull-out shelves (different runner height requirements), and integrated bin positions. A single `FLOOR()` formula cannot encode these. The imos "data ranges" mechanism, which the original correctly described, is actually the right answer here — not a mobile-friendly stepper control.
    
3. **The stepper (+/−) control as proposed creates user-overridable counts without encoding why the auto-count exists.** If a user increases `shelf_count` from 2 to 5 in a 600mm high cabinet, the spacing becomes 90mm — physically impossible for most shelf pins and any door operation clearance. The stepper control as proposed has no guard rail against this.
    

**What survives:** The concept of auto-populated count with user override survives, but only if bounded by validity ranges that are encoded in the template itself, not in ad hoc UI validation.

## ATTACK 5 — THE OFFLINE-FIRST + THOUSANDS OF SKUs CLAIM IS ENTIRELY UNADDRESSED IN THE ORIGINAL

**Verdict: The original completely ignored the hardest technical problem in the entire spec.**

The original document promised to cover "works in demo, dies at scale" failures and specifically named "low-end Android, hundreds of panels, thousands of SKUs, offline-first" as the scale context. It then proposed a mental model that says nothing about data architecture.

Here is what actually happens at that scale:

**SKU catalog loading on low-end Android:**

[21](https://medium.com/yello-offline/building-faster-sqlite-inserts-e732c21bfcfa) Supporting offline-first on mobile devices requires downloading hundreds of thousands of JSON objects and inserting them into SQLite. Loading all client data was taking much longer than acceptable — analysis found the biggest performance bottleneck was 300k translations being written to the database one object at a time.

Our scale: thousands of SKUs × parametric rules per SKU (min/max dimensions, valid combinations, formula strings, hardware compatibility lists) = easily 50,000–200,000 rows of relational data. On a low-end Android device with fragmented storage, this is not a solved problem.

[22](https://oneuptime.com/blog/post/2026-02-06-monitor-sqlite-mobile-apps-opentelemetry/view) Most teams have zero visibility into how SQLite performs once the app ships to users. Queries that ran fine in development can grind to a halt on low-end devices with fragmented storage.

**The relation-table trap:**

[23](https://dev.to/artem_poluektov/mobile-database-optimization-realm-vs-sqlite-3157) The real performance killer is creating relations between entities. A synthetic test writing to a single table may look fine, while the production app with two related tables reveals severe degradation.

A parametric component library has deep relational structure: Template → Parts → Construction Principles → Hardware → Materials → Valid Dimensions → Override History. Every cabinet instance query joins across this entire graph. On a Galaxy A03 with 2GB RAM and 32GB eMMC storage, this is a different device class than the developer's MacBook Pro.

**The proposed "orange dot / update available" notification for library propagation:**

This is a sync problem. The original said nothing about how the sync engine works. [28](https://www.sachith.co.uk/offline-sync-conflict-resolution-patterns-architecture-trade%E2%80%91offs-practical-guide-feb-19-2026/)Not handling partial sync failures or intermittent connectivity can cause lost changes or inconsistent states.

Specifically: a user is offline in a kitchen showroom. They have modified 14 instances of a template. They reconnect. The sync engine tries to reconcile their local overrides with a template update that was published while they were offline. [33](https://appmaster.io/blog/offline-first-background-sync-conflict-retries-ux)One common failure is silent overwrites: if the app uploads an older version and the server accepts it without checking, you can erase someone else's newer edit and nobody notices until it's too late. Sync should use a version number and refuse to overwrite when the server has moved on.

The original proposed no version-vector strategy, no CRDT approach, no conflict-resolution UI beyond "orange dot" — and no tombstone policy for deleted templates. [32](https://www.adalo.com/posts/offline-vs-real-time-sync-managing-data-conflicts)An essential practice for deletion is tombstones — marking deleted items with a "deleted" flag instead of removing them outright, ensuring that deletions persist even if another device updates the same item later.

**What survives from the original's offline discussion:** Nothing. The original did not address offline-first architecture at all. It is entirely absent. This is the biggest gap.

## ATTACK 6 — THE "THREE LAYER STACK" MENTAL MODEL HAS A MISSING LAYER

**Verdict: Structurally incomplete. Will generate technical debt in month 2.**

The original proposed: `Section Template → Configured Assembly → User Library Item`

This is missing the **Validity Contract Layer** — the machine-readable specification of what dimension ranges, part-count ranges, and material combinations are valid for a given template. Without it:

- The conditional count stepper has no guard rails (Attack 4).
- Template updates can propagate constraints that invalidate already-saved user assemblies with no detection signal.
- The CNC/cut-list export has no pre-flight validity check and will produce bad cut lists from technically invalid configurations.

This is exactly the gap that imos's "data ranges" fill (as correctly described in the original) — but the original never ported that concept into its own proposed mental model. It described the source correctly and then forgot to use it.

## ATTACK 7 — THE SHARING MODEL MISSES THE MOST DANGEROUS REAL-WORLD FAILURE

**Target: "Team tier — Cloud-synced shared workspace; explicit publish step."**

**Verdict: The publish step creates a version-cliff problem that will cause data loss across user sessions.**

The original correctly identified that Figma requires an explicit publish step, but did not identify what happens when a publish step creates a breaking structural change while other users have active sessions with instances of the old template.

The community workaround for this in Figma is: [6](https://forum.figma.com/ask-the-community-7/how-to-update-test-library-component-for-breakage-before-publishing-21534)open a new branch, work on the component in the branch, ask others to review it, publish to team first, then jump into a test file that has all components, test for breakage before merging to main.

This is a software engineering branching workflow. The original proposed surfacing this to mobile users as a simple "Publish" button. Non-expert mobile users building their own furniture libraries will not run a branching + QA workflow before publishing a template change. They will tap "Save" and silently break every other user in their team workspace who has instances of that template.

**The strongest alternative for the sharing model:** Semantic versioning on templates with consumer-pinned versions. A user library item pins to `BaseCornerCabinet@v2.1` — not to `BaseCornerCabinet@latest`. Updates are opt-in per-instance, not automatic. This prevents the version cliff entirely. The cost is slightly higher storage (multiple versions of templates on device) and a more complex "upgrade available" UI. The alternative failure it prevents is catastrophic: team member publishes a structural template change, all active sessions across the team have their assembly instances silently invalidated.

### CORRECTIONS TO APPLY (these replace flawed claims from the original)

**Correction 1 — Kill Rule 5 as designed. Replace with pinned semantic versioning.**

Replace: _"All instances in the project receive an 'update available' notification and can accept or reject the update. Accepted updates merge with existing overrides using the layer-ID approach."_

With: Templates are versioned (`v1.0`, `v2.0`, etc.). Instances pin to a specific version at placement time. A user explicitly upgrades an instance — not a batch of instances — to a newer template version. On upgrade, the system shows a diff: "Part `door_panel` renamed to `door_leaf` — your override on this part will be reset." User confirms per-part. No automatic propagation. No silent breakage.

**Correction 2 — Add the Validity Contract as Layer 0.**

The three-layer stack becomes four:

text

```
Layer 0: VALIDITY CONTRACT (machine-readable)
  — min/max H, W, D
  — valid part-count ranges per dimension band
  — material compatibility matrix
  — structural rules (max span without centre support, etc.)

Layer 3: SECTION TEMPLATE (master)
Layer 2: CONFIGURED ASSEMBLY
Layer 1: USER LIBRARY ITEM
```

Layer 0 is checked at: (a) resize, (b) material swap, (c) template upgrade, (d) pre-export to cut list. Any violation blocks or warns before the operation completes.

**Correction 3 — Conditional Count Rule needs guard rails.**

The stepper for shelf count must be bounded by `[min_count(H), max_count(H)]` derived from Layer 0, not open-ended. Any user-input count outside that range is blocked with an explanation ("At this height, 5 shelves would leave 90mm spacing — minimum clearance is 200mm").

**Correction 4 — The offline-first architecture must be specified.**

The original said nothing. Minimum viable spec for the implementing agent:

- **Local storage:** SQLite with Room (Android). [26](https://developer.android.com/topic/performance/sqlite-performance-best-practices)Android recommends the Jetpack Room library. SQLite implements mutations via Write-Ahead Logging (WAL) — WAL should be enabled.
- **Bulk insert pattern:** [21](https://medium.com/yello-offline/building-faster-sqlite-inserts-e732c21bfcfa)Batch inserts for datasets greater than 10,000 rows — individual inserts are the primary bottleneck. SKU catalog must be inserted in batches on first sync, not row-by-row.
- **Template data storage:** Store parametric rule strings as raw JSON blobs in the template row, not as relational sub-tables. [23](https://dev.to/artem_poluektov/mobile-database-optimization-realm-vs-sqlite-3157)Storing raw JSON data directly in the database and mapping on demand — rather than maintaining relational links — produced up to 300× performance improvement in a documented production case. This directly applies to our parametric formula strings, which need fast retrieval but are rarely queried relationally.
- **Sync conflict strategy:** [31](https://www.alphasoftware.com/blog/offline-sync-architecture-tutorial-examples-tools-for-field-operations)Delta syncing sends only changes since the last successful sync using timestamps or version vectors, reducing bandwidth consumption — critical for cellular connections. Use last-write-wins for user configuration data (acceptable loss risk) and explicit conflict UI for template master edits (not acceptable to silently overwrite).
- **Tombstone policy:** [32](https://www.adalo.com/posts/offline-vs-real-time-sync-managing-data-conflicts)Mark deleted templates with a "deleted" flag instead of removing them outright, ensuring deletions persist even if another device updates the same item later.
- **Detection signal for sync failure:** [33](https://appmaster.io/blog/offline-first-background-sync-conflict-retries-ux)Silent overwrites are the most common failure. Use version numbers on every record — refuse to overwrite when the server version has moved on, and surface a clear conflict choice to the user.

**Correction 5 — Remove "Figma as gold standard" framing. Reframe as "Figma as interaction reference with known structural limitations."**

The Push-to-Main feature is explicitly not available for cross-file published libraries. [7](https://help.figma.com/hc/en-us/articles/360039150733-Apply-changes-to-instances)You can only push changes if the main component is in the same file as the instance. It is not possible to push changes to components in another file, including published libraries. This means Rule 6 (Save-Back Rule) as proposed is impossible in the Figma model it claims to borrow from.

### REMAINING RISKS WITH DETECTION SIGNALS

|Risk|Description|Detection Signal|
|---|---|---|
|**Override-wipe on template version upgrade**|User upgrades a template version and loses part-specific overrides silently|Signal: track override count per assembly before and after upgrade; alert if count drops by >20% in a single operation|
|**SQLite performance cliff at scale**|Query latency degrades as local SKU catalog grows past 20k rows on low-end devices|Signal: instrument P99 query time per screen on first-open; alert at >200ms; test on Galaxy A03/A13 class hardware specifically|
|**Formula validity gap**|User-saved template has invalid validity contract (e.g., max shelf count formula allows 0mm spacing)|Signal: run validity contract self-check on every template save; reject any template where min valid spacing < 100mm|
|**Batch sync retry storm**|On reconnect after long offline session, 200+ pending changes hammer the backend simultaneously|Signal: monitor sync queue depth vs. time-to-empty; >100 items in queue triggers throttled exponential backoff|
|**Structural impossibility in cut list**|A configuration passes UI validation but produces a physically invalid cut list (e.g., shelf wider than carcass)|Signal: pre-export validation run — compare every part dimension against its parent assembly envelope; block export if any part exceeds container|
|**Template version sprawl**|Users pin to old template versions and never upgrade; library maintainer cannot deprecate old versions|Signal: track adoption distribution per template version; alert maintainer when >30% of instances are 2+ major versions behind|

### THE GEM THE ORIGINAL MISSED

**The original treated "parametrization" as a purely dimensional problem — what grows and what stays fixed — and missed the temporal problem: what happens to instances when the rules themselves change over time.**

Every real-world parametric system that has scaled (imos regen, Cabinet Vision UCS update, even Figma library publish) has to solve a migration problem: existing instances were configured against version N of the rules; the rules are now version N+1; which instances are now invalid, which are silently wrong, and which can be automatically upgraded?

The original described each tool's save mechanism and propagation model in isolation but never synthesized the insight that **the parametric rule set is itself a versioned artifact that requires a migration strategy, not just a "master update" button.** This is the debt that will be paid in month 6 when the first template breaking change ships and the support queue fills with "my kitchen just lost all its shelves."

The fix is simple in concept but must be built from day one: every template carries a schema version; every instance records the schema version it was configured against; on mismatch, the system runs a declared migration function (or, if none exists, blocks the upgrade and tells the user why). This is exactly how database schema migrations work — and for the same reason. The original's entire mental model omitted it.

## Red-team: strongest claims first (and why they’re dangerous in production)

### 1) “Never let resize mean scale the mesh; always re-evaluate rules”

This is the most confident claim—and the one most likely to detonate at your stated scale (low-end Android, hundreds of panels, thousands of SKUs, offline-first).

**Failure mode A: parametric regeneration is slow, inconsistent, and hard to cancel.**  
This isn’t theoretical—parametric CAD vendors and users have been complaining about “regen/rebuild” pain for decades. Onshape users report large feature trees with regeneration times in the tens of seconds and inconsistency (suppression changes timings, “good days/bad days”), which is exactly what you get when every edit triggers recomputation across dependent features. [1](https://forum.onshape.com/discussion/29134/regeneration-time-is-slow-but-also-not-consistent-what-gives)  
SolidWorks ships dedicated tools just to analyze assembly rebuild time and identifies external references/equations/in-context relationships as rebuild amplifiers—i.e., rule graphs are a first-class performance risk. [2](https://help.solidworks.com/2024/English/SolidWorks/sldworks/HIDD_ASSYXPERT_REBUILD_REPORT.htm)  
Autodesk Fusion explicitly advises performance steps for large files and calls out parametric “timeline/design history” compute time as something you often need to manage. [3](https://help.autodesk.com/view/fusion360/ENU/?caas=caas%2Fsfdcarticles%2Fsfdcarticles%2FPerformance-issues-when-working-with-large-assemblies-in-Fusion-360-and-HSM.html)

**What this means for your mobile app:** “Resize triggers full rule regen” works in a demo with 4 panels. It becomes UI-jank hell when a user drags a cabinet width slider while 200 placed instances recompute hardware patterns, drilling, cutlists, thumbnails, collisions, and pricing. You will end up reinventing “pause rebuild,” “selective rebuild,” “lightweight mode,” and “performance panels”—all things mature CAD had to build because always-on regeneration doesn’t scale. [4](https://forum.onshape.com/discussion/15853/cancel-rebuild)

**Survives?** The _principle_ “don’t geometrically stretch hardware / thickness” is correct. The _implementation_ “always regenerate immediately” does not survive contact with your scale.

---

### 2) “Make parametrization explicit with Fixed / Stretch / Repeat / Lock”

Nice mental model. Still a trap unless you also solve **identity stability** and **graph discipline**.

**Failure mode: topological naming / reference breakage (the silent killer).**  
Parametric systems break when downstream features reference geometry that gets renumbered or replaced after upstream changes. FreeCAD documents this as the “topological naming problem”: face/edge IDs change after recompute, breaking dependent features; fixing becomes tedious and may require disciplined modeling practices (datums, stable references). [5](https://reqrefusion.github.io/FreeCAD-Documentation-html/wiki/Topological_naming_problem.html)  
This is the canonical case study in why “rule-based regeneration” is not enough: you must design a **stable reference system** from day 0, or models “randomly” break when resized.

**Why your proposal is exposed:**  
Your “stretch map” implicitly assumes openings/parts keep semantic identity across resizes (“this opening is locked”). In real parametric engines, identity often degenerates into “the 3rd shelf from the left,” which becomes wrong when a repeat rule adds/removes shelves. That’s exactly the class of breakage FreeCAD warns about. [5](https://reqrefusion.github.io/FreeCAD-Documentation-html/wiki/Topological_naming_problem.html)

**Survives?** The four behaviors are still a good _user-facing vocabulary_—but only if the backend enforces acyclic dependencies + stable semantic IDs (not geometry-derived IDs).

---

### 3) “Use a Figma-like component/instance + overrides model”

Figma is the right benchmark _interaction-wise_, but it’s also evidence of how painful this gets at scale.

**Failure mode A: overrides break after library updates (real shipped pain).**  
A long-running Figma forum thread reports overrides breaking after library publish: layout/alignment/radius resets, nested overrides lost, files freezing during update—making “update from library” feel unreliable. [6](https://forum.figma.com/ask-the-community-7/component-overrides-get-broken-after-library-publish-27231)

**Failure mode B: component/variant scale hits hard memory ceilings.**

## Hidden costs and maintenance traps (specific to your scale)

### A) Performance debt: “regen storm” + UI responsiveness

If every drag/resize triggers regeneration across hundreds of placed sections, you’ll need:

- debounced edits + “apply” vs “preview”

- caching (geometry + derived BOM/pricing)
- cancellation (“pause rebuild”) and batching (edit multiple params then rebuild once)

This is not optional. CAD tools and users explicitly ask for “cancel/pause rebuild” because it’s otherwise unusable on complex models. [4](https://forum.onshape.com/discussion/15853/cancel-rebuild)

Detection signal early: increasing median time-to-interactive during param changes; UI frame drops under “drag width” on low-end devices; “regen queue backlog” grows.

## Strongest alternative / hybrid (and what future failure it prevents)

### Hybrid strategy: **Canonical-parameters + staged compilation (Preview vs Commit vs Manufacture)**

**Core idea:** treat “regenerate rules” as a _compilation step_, not as the default response to every UI tick.

1. **Preview (fast, UI-grade)**
    
    - During dragging/resizing: update _only_ high-level bounding boxes and a simplified layout (no drilling patterns, no hardware placement, no repeats beyond coarse counts).
    - Allow a cheap transform _only as a temporary visual_, never as stored truth (avoid SketchUp’s dual-size-system trap by never persisting the transform; persist only canonical params). [10](https://forums.sketchup.com/t/parametric-sketchup-dynamic-component-stable-setup-common-pitfalls-and-solutions/345817)
2. **Commit (accurate, cancellable)**
    
    - On “Apply” / gesture-end: run rule evaluation incrementally, with cancellation and progress.
    - Cache results by (TemplateVersion, StandardVersion, ParamVectorHash).
3. **Manufacture (heavy, deterministic)**
    
    - CNC drilling, hole rows, hardware machining, costing: computed in a deterministic batch pipeline, not in the interactive loop.
    - This prevents the Onshape/SolidWorks/Fusion “regen storm” from destroying interactivity. [3](https://help.autodesk.com/view/fusion360/ENU/?caas=caas%2Fsfdcarticles%2Fsfdcarticles%2FPerformance-issues-when-working-with-large-assemblies-in-Fusion-360-and-HSM.html)

**Evidence it outperforms:** mature CAD ecosystems explicitly build “performance modes,” regen-time tooling, lightweight/large assembly workflows, and advise users to structure references/versions to improve rebuild performance. That’s basically “staged evaluation + caching” in product form. [18](https://blogs.solidworks.com/solidworksblog/2013/10/improving-performance-of-large-assemblies.html)

**Future failure prevented:** “works in demo, dies at scale” UI jank and unpredictable regen latency.

---

### Library architecture alternative: **Immutable, versioned template packages + pinning**

Instead of “live-edit masters everyone updates to,” ship:

- Templates are **immutable** once published (content-addressed).
- Publishing creates a new version; instances **pin** to a version.
- Updating a job to a new template version is an explicit migration action with preview (“these overrides will be dropped/rewired”).

This is the antidote to Figma-style “update broke my overrides” pain. [6](https://forum.figma.com/ask-the-community-7/component-overrides-get-broken-after-library-publish-27231)  
It also aligns with Onshape guidance that version references and careful structuring can improve document performance and reduce rebuild churn. [19](https://cad.onshape.com/help/Content/Home/performance_considerations.htm)

**Future failure prevented:** silent override corruption after library update + catastrophic “shop floor changed” incidents mid-job.

---

### Parametric rules alternative: **Acyclic DSL + stable semantic IDs**

Don’t let users build arbitrary graphs. Provide a constrained “cabinet rules DSL” that enforces:

- Acyclic dependency graph (no circular rebuild loops)
- Stable identity keys for openings/parts (e.g., `opening.front.leftBay` not “face42”)
- Repeat constructs that explicitly define identity (“first/last/fixed index anchors”)

This is directly motivated by topological naming failures in parametric CAD: arbitrary references to geometry are brittle; you must encode stable references and modeling discipline into the system. [5](https://reqrefusion.github.io/FreeCAD-Documentation-html/wiki/Topological_naming_problem.html)

**Future failure prevented:** “random breakage” of templates after resizing/division changes.

## What survives — explicitly

1. **PolyBoard's recursive zone/cell model.** Deterministic, solver-free, O(tree) evaluation in a single top-down pass — microseconds for hundreds of nodes. Survives every attack above. This is the architecture.
2. **imos division strings** (`450:1:1`). A tiny, declarative, serializable spacing spec, deterministically re-evaluated on resize. Survives; adopt as the spacing primitive.
3. **Proportional-vs-fixed positioning flag.** The whole "scope control" problem collapses to one bit per division. Survives; this is what your scope-switching gesture should toggle.
4. **Nil panels.** Zero-cost virtual nodes; trivially correct in a zone tree. Survives.
5. **Cut list as the non-negotiable minimum.** Confirmed by all eight systems _and_ by PRO100's market success. You've already shipped BOM — that's the right first thing to have shipped.
6. **Mozaik's per-opening Lock Width/Height and row-level Equalize Widths.** The second gem: a "run" container distributing leftover width via a division string gives you **80% of W4I's skeleton value at 0% of its cost** — base/wall rows that re-flow when a run length changes, with no dependency graph.

## The hybrid, and why it outperforms

**Zone tree (PolyBoard) + division strings (imos) + per-zone locks and run-level equalize (Mozaik) + 2D elevation as primary editor (CV/Mozaik practice) + command-pattern undo over immutable tree. No constraint solver. No persisted history. Bazis/PRO100 vocabulary in the UI.**
